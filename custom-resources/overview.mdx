Lumovi has a page of its own for Kubernetes' common kinds. Every other kind the cluster serves, custom resources and Kubernetes' less common kinds alike, is found through API discovery and works the same way: a list, a status, a detail panel, YAML, create, edit and delete.

⌘ is Ctrl on Windows and Linux. The palette's search also knows "CRDs", so typing it finds **API resources**. It finds a plugin by the name of any of its kinds too: `certificates` offers **cert-manager**.

### API resources

**API resources** lists every kind the cluster serves in two tables: **Custom resources**, grouped by API group, and **Kubernetes**. For each kind you see its short names, **API version**, **Scope** (namespaced or cluster-wide) and, under **Shown by**, what shows it: a plugin, a file of yours, **Lumovi**, or nothing in particular. **Filter kinds** matches names, short names, plurals and groups.

Lumovi looks at what the cluster serves again every minute, so a CRD you just installed shows up on its own.

### A short sidebar, however many CRDs

A cluster can have hundreds of custom resource definitions, so the sidebar doesn't list them all:

- **Plugins.** Each tool the cluster runs, like Flux or cert-manager, gets an entry that leads to all its kinds. Most are under **Plugins**; a few that extend Kubernetes' own, like Gateway API, sit in **Network**, **Configuration** or **Storage**. See [Plugins](/custom-resources/plugins).
- **Custom resources.** The kinds you opened most recently in this cluster, up to five, and **API resources**, with a count of every custom kind the cluster serves. Kinds that belong to a plugin are left out, since its entry is a click away already.

To keep a kind at hand, **pin** it: use the pin button on its list, or next to it in **API resources**. Pinned kinds get a **Pinned** section in the sidebar, in every cluster that serves them.

## What you see

### Columns

A kind's list has the columns the API server prints for it, the same ones `kubectl get` shows (a CRD's printer columns). A [view](#views) can replace them with better ones.

### Status

Each object gets a status read from the conventions most controllers follow, checked in this order:

<Steps>
  <Step title="Being deleted">
    <span className="lumovi-status warning">Terminating</span>
  </Step>
  <Step title="Turned off">
    `spec.suspend` gives <span className="lumovi-status neutral">Suspended</span>, and `spec.paused` gives <span className="lumovi-status neutral">Paused</span>.
  </Step>
  <Step title="Stuck">
    A `Stalled` condition that's `True` (as [kstatus](https://github.com/kubernetes-sigs/cli-utils/tree/master/pkg/kstatus) defines it) is <span className="lumovi-status critical">critical</span>, labeled with its reason.
  </Step>
  <Step title="Its main condition is False">
    The first of `Ready`, `Available`, `Healthy`, `Programmed`, `Established`, `Succeeded` or `Accepted` that it has. If it's `False`, the object is <span className="lumovi-status critical">critical</span>, labeled with its reason, unless the object says it's still working on it.
  </Step>
  <Step title="Catching up">
    A `Reconciling` or `Issuing` condition that's `True`, or a spec the controller hasn't caught up with yet (`status.observedGeneration` behind `metadata.generation`), is progressing: <span className="lumovi-status progressing">Reconciling</span>, or the condition's reason.
  </Step>
  <Step title="Its main condition is True">
    `True` is <span className="lumovi-status healthy">healthy</span>, labeled with the condition's name, like Ready. `Unknown` is progressing.
  </Step>
  <Step title="A health or a phase">
    Failing that, an Argo-style `status.health.status`, or `status.phase` or `status.state`, read by its words: "Failed" or "Degraded" are critical, "Pending" or "Provisioning" are progressing, "Running" or "Bound" are healthy, and so on.
  </Step>
</Steps>

Objects with none of these show <span className="lumovi-status neutral">Unknown</span>, and are never sorted above real problems. A view's status rules take over from all of this. See [Health and status](/explore/health) for how statuses sort and filter.

### The detail panel

Click an object to open it. Its **Overview** has its details, its conditions, the objects it links to under **Related** (when a view says), and its **Spec** and **Status** as trees you can fold.

A view can also list the objects that belong to this one, a tab each: a node pool's **Nodes**, a pipeline's **Runs**. A list of pods becomes the **Pods** tab, under the view's name for it (CloudNativePG's **Instances**), with **Logs** and **Metrics** tabs for those pods.

On Kubernetes 1.27 and later, Lumovi reads each kind's schema from the cluster's OpenAPI documents, and explains every field when you hover it. Custom resources publish their CRD's schema there too, so their fields are explained the same way.

## What you can do

Custom resources are first-class:

- **Create** them from YAML (<kbd>⌘</kbd><kbd>N</kbd> in the desktop app), checked by the cluster before anything is created. The cluster has to serve a kind before you can create objects of it, so create a new CRD on its own first. See [Create objects](/changes/create).
- **Edit** their YAML or labels. Edits are validated by the cluster against the CRD's schema with a dry run, and shown as a diff before they're saved. See [Edit YAML](/changes/yaml).
- **Delete** them, one or many at once. Deleting a CustomResourceDefinition asks you to type its name first, since it deletes every object of that kind.
- **Scale** kinds that have the scale subresource, like Argo Rollouts, the same way as a Deployment.
- Use the **actions** a view adds, like Flux's **Reconcile**, Argo CD's **Sync**, or CloudNativePG's **Back up now…**, which creates a backup.

Every change checks your permissions first, and shows the equivalent `kubectl` command, written like `kubectl delete certificate.cert-manager.io/api-tls -n shop --context production`.

## Plugins

A **plugin** tells Lumovi about the kinds of one tool. It can give the tool a place in the sidebar: one entry, leading to a page that lists everything of its kinds together, what's failing first, with a tab for each kind. And it holds the tool's [views](#views).

Lumovi comes with plugins for 32 tools and shows the ones your cluster runs. You can write your own, or put one of yours in place of one of Lumovi's. **API resources** says what shows each kind. [All plugins](/custom-resources/plugins#every-plugin-on-one-page) lists every plugin with what it asks for, and anything wrong with yours: a plugin with a problem isn't used at all, and each message says where the problem is.

### Views

A **view** is the part of a plugin that says how one kind is shown: which columns matter, how to tell whether an object is healthy, which facts to show, which objects it links to and which belong to it, and which changes people make to it. A view is data: it reads fields, and runs no code. Four of Lumovi's plugins also draw [pages with code of their own](/custom-resources/plugins#pages-drawn-by-a-plugin’s-code), in a sandbox.
