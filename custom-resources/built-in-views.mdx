Lumovi ships an add-on and views for the tools most clusters run. When a cluster serves one of a tool's kinds:

- **Its add-on** gives the tool an entry in the sidebar. It leads to everything of the tool's kinds in one list, what's failing first, with a tab for each kind. See [Add-ons](/custom-resources/add-ons).
- **Its views** give each kind the columns people look at first, a status that understands the tool, links to the objects it points to, tabs for the objects that belong to it, and the changes its own CLI offers, as actions.

Each section below names the add-on, where it sits in the sidebar, and its kinds in the order of their tabs, then what each kind's view adds. A kind without a view shows the columns the API server prints, and a status read from [the usual conventions](/custom-resources/overview#status).

A related tab of pods takes its place as the detail panel's **Pods** tab, under its own name, and comes with **Logs** and **Metrics** tabs for those pods.

Like every change in Lumovi, a view's actions check your permissions first: `patch` on the kind (or on its `status`), or `create` on the kind an action creates. They show the equivalent command, `kubectl patch` or `kubectl create`, and are refused in a [read-only](/changes/read-only) cluster. In the tables:

- An action whose name ends in **…** asks first.
- **undo**: it can be taken back from its notification.
- **asks**: it asks for a value, like which instance becomes the primary.
- **creates**: it creates an object, shown as YAML before it's created.

## Argo CD and Argo Rollouts

[Argo CD](https://argo-cd.readthedocs.io) applications, and [Argo Rollouts](https://argoproj.github.io/rollouts). They're two add-ons:

- **Argo CD**, under **Add-ons** (`argo-cd`): Application, ApplicationSet, AppProject.
- **Argo Rollouts**, under **Add-ons** (`argo-rollouts`): Rollout, AnalysisRun, AnalysisTemplate, ClusterAnalysisTemplate, Experiment.

Applications and rollouts have views; the other kinds don't. Applications take their status from Argo CD's own health: <span className="lumovi-status healthy">Healthy</span>, <span className="lumovi-status progressing">Progressing</span>, <span className="lumovi-status critical">Degraded</span>, <span className="lumovi-status warning">Missing</span> or <span className="lumovi-status neutral">Suspended</span>. A rollout is <span className="lumovi-status healthy">Healthy</span>, <span className="lumovi-status neutral">Paused</span>, <span className="lumovi-status critical">Degraded</span>, <span className="lumovi-status critical">Aborted</span>, or in progress with its phase.

| Kind | Columns | Links | Actions |
| --- | --- | --- | --- |
| Application | Sync, Repository, Path, Destination | Destination | **Sync**, **Refresh** |
| Rollout | Desired, Ready, Updated, Steps | | **Promote**, **Resume** (undo), **Restart…**, **Abort…** |

- **Sync** starts a sync, like the Sync button in Argo CD. It's offered when no operation is running.
- **Refresh** asks Argo CD to compare the application with its source again.
- An application's **Destination** link opens the namespace it deploys to.
- **Promote** moves a paused rollout past its pause. **Resume** unpauses one that was paused by hand.
- **Restart…** replaces the rollout's pods a few at a time, as its strategy says. It asks first.
- **Abort…** stops a rollout in progress and sends traffic back to the stable version. It's destructive, so it asks first.

Rollouts have the scale subresource, so you can also **Scale** them like a Deployment.

## Argo Workflows

[Argo Workflows](https://argoproj.github.io/workflows): workflows, their templates and schedules.

**Argo Workflows**, under **Add-ons** (`argo-workflows`): Workflow, CronWorkflow, WorkflowTemplate, ClusterWorkflowTemplate.

A workflow is <span className="lumovi-status healthy">Succeeded</span>, <span className="lumovi-status neutral">Suspended</span>, <span className="lumovi-status progressing">Stopping</span>, critical when it failed or hit an error, and otherwise in progress with its phase. A cron workflow is <span className="lumovi-status healthy">Scheduled</span>, <span className="lumovi-status neutral">Suspended</span>, <span className="lumovi-status neutral">Stopped</span>, or <span className="lumovi-status critical">Can't submit</span> when it couldn't start a run.

| Kind | Columns | Links | Related tabs | Actions |
| --- | --- | --- | --- | --- |
| Workflow | Progress, Started, Finished, Template | Template, Cron workflow | **Pods** | **Suspend** (undo), **Resume** (undo), **Stop…**, **Terminate…**, **Resubmit…** (creates) |
| CronWorkflow | Schedules, Last run, Running | | **Runs** | **Submit now…** (creates), **Suspend** (undo), **Resume** (undo) |
| WorkflowTemplate | Entrypoint, Parameters | | **Runs** | **Submit…** (creates) |
| ClusterWorkflowTemplate | Entrypoint, Parameters | | | |

- **Suspend** pauses a running workflow, and **Resume** picks it up again.
- **Stop…** stops the steps running now, and its exit handlers still run. **Terminate…** stops everything at once, exit handlers included; it's destructive. Both are offered while a workflow is pending or running.
- **Resubmit…** creates a new workflow with a finished one's spec.
- **Submit now…** creates a workflow from a cron workflow's spec, without waiting for its schedule. **Submit…** creates one that runs a template.
- **Runs** lists the workflows a cron workflow or a template started.

## CloudNativePG

[CloudNativePG](https://cloudnative-pg.io): PostgreSQL clusters and their backups.

**CloudNativePG**, under **Add-ons** (`cloudnative-pg`): Cluster, Pooler, Backup, ScheduledBackup, Database. Poolers and databases have no view.

A cluster is <span className="lumovi-status healthy">Healthy</span>, critical with its phase when that speaks of a failure or an error, and otherwise in progress with its phase. A backup is <span className="lumovi-status healthy">Completed</span>, <span className="lumovi-status critical">Failed</span>, or in progress with its phase.

| Kind | Columns | Links | Related tabs | Actions |
| --- | --- | --- | --- | --- |
| Cluster | Instances, Ready, Primary | Primary | **Instances**, **Volumes** | **Back up now…** (asks, creates), **Switch over…** (asks), **Restart…** |
| Backup | Cluster, Method, Started | Cluster | | |
| ScheduledBackup | Schedule, Last, Next | Cluster | **Backups** | **Suspend** (undo), **Resume** (undo) |

- **Instances** lists the cluster's instance pods, with their logs and usage. **Volumes** lists its volume claims.
- **Back up now…** asks for the **Method**, `barmanObjectStore` or `volumeSnapshot`, and creates a Backup of the cluster.
- **Switch over…** asks which instance is the **New primary**. The current primary becomes a replica, and connections to the primary drop for a moment. It's offered when the cluster has two instances or more, and patches the cluster's status, so it needs `patch` on its `status`.
- **Restart…** restarts the instances one at a time, replicas first and the primary last, with a switchover. It asks first.
- **Backups** lists the backups a scheduled backup made.

## Flux

[Flux](https://fluxcd.io): what it applies, and where it fetches it from.

**Flux**, under **Add-ons** (`flux`): Kustomization, HelmRelease, GitRepository, OCIRepository, HelmRepository, HelmChart, Bucket.

Statuses follow Flux's conditions: <span className="lumovi-status neutral">Suspended</span>, <span className="lumovi-status critical">Stalled</span>, <span className="lumovi-status progressing">Reconciling</span> or <span className="lumovi-status healthy">Ready</span>, or critical with Flux's reason.

| Kind | Columns | Links | Actions |
| --- | --- | --- | --- |
| Kustomization | Revision, Path, Source | Source | **Reconcile**, **Suspend** (undo), **Resume** (undo) |

A Helm release that Flux manages links to its HelmRelease from [Helm releases](/helm/releases#releases-flux-manages).

## KEDA

[KEDA](https://keda.sh): event-driven autoscaling of workloads and jobs.

**KEDA**, under **Add-ons** (`keda`): ScaledObject, ScaledJob, TriggerAuthentication, ClusterTriggerAuthentication. Trigger authentications have no view.

A scaled object is <span className="lumovi-status healthy">Scaling</span> or <span className="lumovi-status healthy">Idle</span>, <span className="lumovi-status neutral">Paused</span>, <span className="lumovi-status neutral">Paused at 2</span> with the replicas it's held at, or critical with KEDA's reason.

| Kind | Columns | Links | Related tabs | Actions |
| --- | --- | --- | --- | --- |
| ScaledObject | Target, Min, Max, Triggers | Target, Autoscaler | | **Pause** (undo), **Pause at…** (undo, asks), **Resume** |
| ScaledJob | Max, Triggers | | **Jobs** | |

- **Pause** sets KEDA's `autoscaling.keda.sh/paused` annotation: autoscaling stops, and the target keeps its replicas.

- **Resume** removes both annotations. It has no undo: pause again instead.
- **Jobs** lists the Jobs a scaled job started.

## Changing a built-in view

Your own view of a kind replaces Lumovi's for that kind, and your own add-on replaces Lumovi's add-on with the same name: the one each section above gives after the add-on's label, like `flux`. Copy the file you want to change from [Lumovi's views](https://github.com/Lumovi/Lumovi/tree/main/src/renderer/src/views) into `~/.lumovi/views`, edit it, and press <kbd>⌘</kbd><kbd>R</kbd> (Ctrl+R on Windows and Linux). **API resources** then shows your file as the kind's view.

Views replace each other kind by kind: a view of yours for one of a tool's kinds leaves Lumovi's views of its other kinds in place. See [Which view a kind uses](/reference/view-format#which-view-a-kind-uses).

<Note>
  **In your cluster:** put your views and add-ons in the chart's `views` value. See [Views for everyone](/server/views).
</Note>

## Contributing a view

Adding a tool needs no code, and is a welcome first contribution. To ask for one instead, open a [Support a tool](https://github.com/Lumovi/Lumovi/issues/new?template=tool_request.yml) issue. The [contributing guide](https://github.com/Lumovi/Lumovi/blob/main/CONTRIBUTING.md#adding-a-tool) has the details; in short:

<Steps>
  <Step title="Pin the tool's CRDs">
    Add its release to `tests/views/crds/sources.json`, under the add-on's name, with the URLs of its CRD manifests, and run `npm run crds -- <name>`. That keeps what the check needs of them in `tests/views/crds/<name>.json`. A chart's templates work too, and for a tool whose operator creates its CRDs itself, the JSON Schema of each kind will do.
  </Step>
  <Step title="Write its add-on and views">
    Write `src/renderer/src/views/<name>.yaml`, with a comment linking to the tool: the `AddOn`, then a `View` for each kind (or group of kinds) worth more than the generic columns. Status rules are where views help most: say what healthy, in progress, failing and paused look like for this tool.
  </Step>
  <Step title="Check it">
    Run `npm run views:check`. It checks every kind, path, template, link, related list and action against the CRDs you pinned, so a misremembered field fails there rather than showing nothing. Labels and annotations aren't in schemas, so check those against the tool's documentation, or a real cluster.
  </Step>
  <Step title="Look at it">
    Put the file in `~/.lumovi/views` while running `npm run dev` against a cluster with the tool installed, and press <kbd>⌘</kbd><kbd>R</kbd> after each change.
  </Step>
</Steps>

To check the views against a newer release of a tool, change its version in `sources.json`, and run `npm run crds -- <name>` and `npm run views:check`.
