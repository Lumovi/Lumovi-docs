Lumovi comes with a plugin for each of the tools most clusters run. When a cluster serves one of a tool's kinds:

- **Its place in the sidebar** gives the tool an entry. It leads to everything of the tool's kinds in one list, what's failing first, with a tab for each kind. See [Plugins](/custom-resources/plugins).
- **Its views** give each of its kinds the columns people look at first, a status that understands the tool, links to the objects it points to, tabs for the objects that belong to it, and the changes its own CLI offers, as actions.

Each section below names the plugin, where it sits in the sidebar, and its kinds in the order of their tabs, then what each kind's view adds. A kind without a view shows the columns the API server prints, and a status read from [the usual conventions](/custom-resources/overview#status).

A related tab of pods takes its place as the detail panel's **Pods** tab, under its own name, and comes with **Logs** and **Metrics** tabs for those pods.

Like every change in Lumovi, a view's actions check your permissions first: `patch` on the kind (or on its `status`), or `create` on the kind an action creates. They show the equivalent command, `kubectl patch` or `kubectl create`, and are refused in a [read-only](/changes/read-only) cluster. In the tables:

- An action whose name ends in **…** asks first.
- **undo**: it can be taken back from its notification.
- **asks**: it asks for a value, like which instance becomes the primary.
- **creates**: it creates an object, shown as YAML before it's created.

## Where they come from

The included plugins live in their own repository, [Lumovi-plugins](https://github.com/Lumovi/Lumovi-plugins). Every change there is checked by Lumovi's own checker against its tool's CRDs, and they're released together, as one bundle: built, signed and attested by the repository's release workflow, from the commit on `main` that the release's tag points at.

Each Lumovi release is built with one of those releases, which it pins by its SHA-256 and names in its release notes. As Lumovi is built, the bundle is checked again: its SHA-256 and its index's, its signature by Lumovi-plugins' release workflow on `main`, its attestation that it was built from the commit the tag points at, and each plugin's file against the index. If any of it doesn't hold, Lumovi isn't built. Lumovi pins only releases that can't be changed once published. So the plugins in a Lumovi release are the bundle it names, and nothing can be swapped in or added once it's out.

To check a release of the plugins yourself, with the [GitHub CLI](https://cli.github.com) (`<version>` is the one your Lumovi's release notes name):

```bash
gh release download v<version> --repo Lumovi/Lumovi-plugins
gh attestation verify plugins-<version>.json --repo Lumovi/Lumovi-plugins \
  --signer-workflow Lumovi/Lumovi-plugins/.github/workflows/release.yml \
  --source-ref refs/heads/main
```

## Argo CD and Argo Rollouts

[Argo CD](https://argo-cd.readthedocs.io) applications, and [Argo Rollouts](https://argoproj.github.io/rollouts). They're two plugins:

- **Argo CD**, under **Plugins** (`argo-cd`): Application, ApplicationSet, AppProject.
- **Argo Rollouts**, under **Plugins** (`argo-rollouts`): Rollout, AnalysisRun, AnalysisTemplate, ClusterAnalysisTemplate, Experiment.

Applications and rollouts have views; the other kinds don't. Applications take their status from Argo CD's own health: <span className="lumovi-status healthy">Healthy</span>, <span className="lumovi-status progressing">Progressing</span>, <span className="lumovi-status critical">Degraded</span>, <span className="lumovi-status warning">Missing</span> or <span className="lumovi-status neutral">Suspended</span>. A rollout is <span className="lumovi-status healthy">Healthy</span>, <span className="lumovi-status neutral">Paused</span>, <span className="lumovi-status critical">Degraded</span>, <span className="lumovi-status critical">Aborted</span>, or in progress with its phase.

| Kind | Columns | Links | Actions |
| --- | --- | --- | --- |
| Application | Sync, Repository, Path, Namespace | Namespace | **Sync…**, **Terminate sync…**, **Refresh** |
| Rollout | Desired, Ready, Updated, Steps | | **Promote**, **Resume** (undo), **Restart…**, **Abort…** |

- **Sync…** asks first, then has Argo CD bring the application in line with its source: at a **Revision** you give (empty: the one it tracks), with **Prune** and a **Strategy**. Pruning is drawn in red and named on the button, **Sync and prune**. It sends the application's own sync options too, as Argo CD's own sync does, so `CreateNamespace=true` and the rest hold; where they include `Replace=true` or `Force=true`, that's drawn in red too. While a sync runs, **Sync** stays where it was, busy, and says how long it has run.
- **Terminate sync…**, while a sync runs or waits to start, asks first, then stops it as Argo CD's own Terminate does, or takes back one Argo CD hasn't started. Lumovi reads the application again as it's sent: if the sync you saw has started, ended or been replaced since, nothing is sent.
- **Refresh** asks Argo CD to compare the application with its source again.
- **Sync…** and **Refresh** are also offered for the applications you select on the plugin's Applications page, asked once for all, without a revision: each syncs to the one it tracks. Lumovi follows each sync to how it ended.
- An application's **Namespace** link opens the namespace it deploys to; its details say its cluster too.
- **Promote** moves a paused rollout past its pause. **Resume** unpauses one that was paused by hand.
- **Restart…** replaces the rollout's pods a few at a time, as its strategy says. It asks first.
- **Abort…** stops a rollout in progress and sends traffic back to the stable version. It's destructive, so it asks first.

Rollouts have the scale subresource, so you can also **Scale** them like a Deployment.

Argo CD's plugin draws pages of its own, with its [code](/custom-resources/plugins#pages-drawn-by-a-plugin’s-code):

- **Overview**, its first tab: four tiles (healthy, synced, syncing now, last sync failed), then what wants a look, worst first; the syncs running now, where each is and what it waits on; health and sync broken down; the syncs that ended last; projects and where the applications run; and ApplicationSets, with what each makes its applications from. Its tiles and counts open the Applications page, filtered to what they count.
- **Applications**, which is also the tab Lumovi shows for the Application kind: every application in one table, searched by name and filtered by health, sync, operation, project, cluster, namespace and auto-sync in Lumovi's own bar, the plugin told nothing of what's typed or set there. Its rows can be selected, for **Sync…** and **Refresh**.
- **Argo CD**, a tab on each Application: its health and, beside it, what's happening to it; while a sync runs, where it is, hook phase by phase and wave by wave, and what it waits on, a hook by its name; its revision, last sync (the last one that finished) and auto-sync; its resources as a graph, those out of sync marked; its sync's result, resource by resource; its problems in one place; and its history. Where it deploys to the cluster Lumovi is connected to, the graph goes down to its Deployments' ReplicaSets and their Pods, each card opens what it is, and its problems include the warning events of those that aren't well. A resource's row opens Lumovi's own list of its kind at that one object, for Deployments, StatefulSets, DaemonSets, Services, ConfigMaps, Ingresses, Jobs and CronJobs: the list is Lumovi's, and the plugin reads nothing of it.
- On that tab, [changes it proposes](/custom-resources/plugins#changes-a-page-proposes), each confirmed in Lumovi's own dialog: **Sync…**, with every option Argo CD's own sync has (a revision; prune, dry run, apply only and force; its sync options; retry; and only some resources); **Refresh** (normal or hard); **Delete…**, saying what happens to what it deployed; auto-sync turned on (prune and self-heal asked first) or off; and **Roll back…** to an entry of its history, as Argo CD's own Rollback does, off while auto-sync is on, a sync runs, or it's being deleted. What does harm, as its file says (prune, force, replace, and syncing only some resources), is drawn in red and named on the button; a dry run changes nothing, and its button says **Dry run**.

Besides Argo CD's own kinds, its pages read ReplicaSets and Pods: who made each and how ready it is, never what they run, and the warning events of those that aren't well, each message cut where it could carry something only you may read. Wherever its pages don't run, the view's **Sync…**, **Terminate sync…** and **Refresh** stay on Lumovi's list of Applications.

## Argo Workflows

[Argo Workflows](https://argoproj.github.io/workflows): workflows, their templates and schedules.

**Argo Workflows**, under **Plugins** (`argo-workflows`): Workflow, CronWorkflow, WorkflowTemplate, ClusterWorkflowTemplate.

A workflow is <span className="lumovi-status healthy">Succeeded</span>, <span className="lumovi-status neutral">Suspended</span>, <span className="lumovi-status progressing">Stopping</span>, critical when it failed or hit an error, and otherwise in progress with its phase. A cron workflow is <span className="lumovi-status healthy">Scheduled</span>, <span className="lumovi-status neutral">Suspended</span>, <span className="lumovi-status neutral">Stopped</span>, or <span className="lumovi-status critical">Can't submit</span> when it couldn't start a run.

| Kind | Columns | Links | Related tabs | Actions |
| --- | --- | --- | --- | --- |
| Workflow | Progress, Started, Finished, Template | Template, Cron workflow | **Pods** | **Suspend** (undo), **Resume** (undo), **Stop…**, **Terminate…**, **Resubmit…** (creates) |
| CronWorkflow | Schedules, Last run, Running | | **Runs** | **Submit now…** (creates), **Suspend** (undo), **Resume** (undo) |
| WorkflowTemplate | Entrypoint, Parameters | | **Runs** | **Submit…** (creates) |
| ClusterWorkflowTemplate | Entrypoint, Parameters | | | |

- **Suspend** pauses a running workflow, and **Resume** picks it up again.
- **Stop…** stops the steps running now, and its exit handlers still run. **Terminate…** stops everything at once, exit handlers included; it's destructive. Both are offered while a workflow is pending or running.
- **Resubmit…** creates a new workflow with a finished one's spec.
- **Submit now…** creates a workflow from a cron workflow's spec, without waiting for its schedule. **Submit…** creates one that runs a template.
- **Runs** lists the workflows a cron workflow or a template started.

## CloudNativePG

[CloudNativePG](https://cloudnative-pg.io): PostgreSQL clusters and their backups.

**CloudNativePG**, under **Plugins** (`cloudnative-pg`): Cluster, Pooler, Backup, ScheduledBackup, Database. Poolers and databases have no view.

A cluster is <span className="lumovi-status healthy">Healthy</span>, critical with its phase when that speaks of a failure or an error, and otherwise in progress with its phase. A backup is <span className="lumovi-status healthy">Completed</span>, <span className="lumovi-status critical">Failed</span>, or in progress with its phase.

| Kind | Columns | Links | Related tabs | Actions |
| --- | --- | --- | --- | --- |
| Cluster | Instances, Ready, Primary | Primary | **Instances**, **Volumes** | **Back up now…** (asks, creates), **Switch over…** (asks), **Restart…** |
| Backup | Cluster, Method, Started | Cluster | | |
| ScheduledBackup | Schedule, Last, Next | Cluster | **Backups** | **Suspend** (undo), **Resume** (undo) |

- **Instances** lists the cluster's instance pods, with their logs and usage. **Volumes** lists its volume claims.
- **Back up now…** asks for the **Method**, `barmanObjectStore` or `volumeSnapshot`, and creates a Backup of the cluster.
- **Switch over…** asks which instance is the **New primary**. The current primary becomes a replica, and connections to the primary drop for a moment. It's offered when the cluster has two instances or more, and patches the cluster's status, so it needs `patch` on its `status`.
- **Restart…** restarts the instances one at a time, replicas first and the primary last, with a switchover. It asks first.
- **Backups** lists the backups a scheduled backup made.

CloudNativePG's plugin draws two pages of its own, with its [code](/custom-resources/plugins#pages-drawn-by-a-plugin’s-code):

- **Overview**: every PostgreSQL cluster, what's failing first, and the one you pick, with its status and why, how many instances are ready, its primary, its last backup, and its PostgreSQL version; then its instances with their role, status, node and restarts, its backups, latest first, its schedules, said in words, and its poolers. A backup's row opens it in Lumovi, and an instance's row opens that pod at its **Logs** tab. Under them is the primary's log, which Lumovi reads and draws: the plugin's code never holds a line of it.
- **Backup health**: how many backups ran in the last day and how many failed, which clusters have had no backup in a day, and the next one scheduled; then every cluster's backups, latest first, a cluster with a failed or missing backup above the rest.
- **Shell into primary** and **Forward 5432**, beside it, [link to Lumovi's own places](/custom-resources/plugins#links-to-lumovi’s-own-places) for the primary's pod: its **Shell** tab, and **Port forward** at PostgreSQL's port. A link only says where to go: a shell or a forward still starts only when you start it there.
- **Back up now…** on the cluster you pick is a [change it proposes](/custom-resources/plugins#changes-a-page-proposes): a Backup of that cluster, by the method you pick where it has more than one, which you confirm in Lumovi's own dialog. It can't be pressed while a backup of the cluster runs, or where the cluster has no backup method. Where Lumovi can't read its backups, it says "Couldn’t read its backups, so one may be running."

Its pages read its own kinds and, of pods, only its instances' (labeled `cnpg.io/cluster`): their names, namespaces, labels, ages, nodes, conditions and restarts. Wherever they don't run, the view's **Back up now…**, **Switch over…** and **Restart…** stay on Lumovi's list of clusters.

## Karpenter

Prometheus Operator's plugin draws a page of its own, with its [code](/custom-resources/plugins#pages-drawn-by-a-plugin’s-code):

- **Target health**: how many scrape targets are up, down and not scraped yet; the targets that are down, in one list, each with its last error; then a card for each namespace’s Prometheus, with its scrape pools, worst first, named for the ServiceMonitor, PodMonitor or Probe they come from, and each pool’s targets.

  From Prometheus Operator 1.1.4 (Lumovi-plugins 1.4.1: in the desktop app, **Update…** under [Newer plugins](/custom-resources/plugins#newer-plugins) installs it), the counts are of what was read. ## Changing one of Lumovi's

A plugin of yours with the name of one of Lumovi's is used in its place, all of it. The name is the one each section above gives after the plugin's label, like `flux`. Copy the file you want to change from [Lumovi's plugins](https://github.com/Lumovi/Lumovi/tree/main/plugins) into `~/.lumovi/plugins`, edit it, and press <kbd>⌘</kbd><kbd>R</kbd> (Ctrl+R on Windows and Linux). **API resources** then names your file under **Shown by** for its kinds, and [All plugins](/custom-resources/plugins#every-plugin-on-one-page) says on its row that it's in use in place of Lumovi's. If your copy has a problem, none of it is used, and its row says that Lumovi's is shown instead.

It's the whole plugin or none of it: a kind is one plugin's, so a plugin of yours under another name can't show a kind one of Lumovi's has. See [Whose a kind is](/reference/plugin-format#whose-a-kind-is).

<Note>
  **In your cluster:** put your plugins in the chart's `plugins` value. See [Plugins for everyone](/server/plugins).
</Note>

## Contributing a plugin

Adding a tool needs no code, and is a welcome first contribution. To ask for one instead, open a [Support a tool](https://github.com/Lumovi/Lumovi/issues/new?template=tool_request.yml) issue.

The plugins live in [Lumovi-plugins](https://github.com/Lumovi/Lumovi-plugins), a folder each under `plugins/`. Its [contributing guide](https://github.com/Lumovi/Lumovi-plugins/blob/main/CONTRIBUTING.md) has the details, and how to set up the checks; in short:

<Steps>
  <Step title="Make its folder">
    Make `plugins/<name>/`, named as the plugin is, with its four files: `plugin.yaml`, `README.md` (what it's for, in a line), `crd-sources.json`, and `crds.json`, which the next step writes.
  </Step>
  <Step title="Pin the tool's CRDs">
    In `crd-sources.json`, name the tool's release and the URLs of its CRD manifests, and run `npm run crds -- <name>`. That keeps what the check needs of them in `crds.json`.
  </Step>
  <Step title="Write its plugin">
    In `plugin.yaml`, with a comment linking to the tool: one `kind: Plugin`, with its label and kinds, and under `views:` a view for each kind (or group of kinds) worth more than the generic columns. Status rules are where views help most: say what healthy, in progress, failing and paused look like for this tool.
  </Step>
  <Step title="Check it">
    Run `npm run check`. It runs Lumovi's own checker, which checks every kind, path, template, link, related list and action against the CRDs you pinned, so a misremembered field fails there rather than showing nothing. Labels and annotations aren't in schemas, so check those against the tool's documentation, or a real cluster.
  </Step>
  <Step title="Look at it">
    Put `plugin.yaml` in `~/.lumovi/plugins`, under the plugin's name (`<name>.yaml`), while Lumovi runs against a cluster with the tool installed, and press <kbd>⌘</kbd><kbd>R</kbd> after each change. It's read as one of yours, held to the same checks.
  </Step>
</Steps>

To check a plugin against a newer release of a tool, raise its version in `crd-sources.json`, run `npm run crds -- <name>` and `npm run check`, and raise the plugin's `spec.version`.
