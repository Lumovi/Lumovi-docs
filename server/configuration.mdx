The Helm chart sets these from its [values](/server/helm-values). They're for running the image another way, such as [with Docker](/server/docker), and for the few settings the chart has no value for, which you can set with `extraEnv`.

Lumovi reads them when it starts, and checks most of them: one that doesn't make sense stops it, and its log says which and why. A few aren't checked. `LUMOVI_READ_ONLY` and `LUMOVI_ALLOW_PRIVATE_CHARTS` are on only when they're exactly `true` or `1`, and anything else leaves them off. `LUMOVI_MAX_LIST_ITEMS` and `LUMOVI_REQUEST_TIMEOUT_MS` keep their defaults when they aren't numbers. `LUMOVI_HELM` and `LUMOVI_ARTIFACT_HUB_URL` are used as they are, so a wrong one shows up only when someone uses Helm.

## Set by the chart itself

The chart sets a few of these without a value of its own: `LUMOVI_PORT` to `8080`, the port its Service, probes and network policy point at, `LUMOVI_VIEWS_DIR` to `/etc/lumovi/views`, where it mounts the [views everyone sees](/server/views), with `audit.persistence`, `LUMOVI_AUDIT_DIR` to `/var/lib/lumovi/audit`, where it mounts the [audit history's volume](/server/audit-log#where-it’s-kept), with `access.admins`, `LUMOVI_ACCESS_CONFIGMAP` to `<release>-access`, the ConfigMap it makes for [access](/server/access#where-it’s-kept), with `auth.keepSessions`, `LUMOVI_STATE_SECRET` to `<release>-state`, the Secret it makes to keep sessions across restarts, and `LUMOVI_STATE_KEY` from the Secret of the key they're sealed with, and in a fleet with `fleet.kubeconfigSecret`, `LUMOVI_FLEET_KUBECONFIG_FILE` to `/etc/lumovi/fleet/kubeconfig`, where it mounts that Secret. For an [agent](/server/fleet/agents), it sets `LUMOVI_AGENT_HEALTH_PORT` to `8081`, where its probes point. Leave these out of `extraEnv`.

The chart puts `extraEnv` after its own variables. When two have the same name, Kubernetes uses the last, so a variable repeated in `extraEnv` wins over the chart's. For the ones above, that breaks Lumovi: it listens on a port nothing sends to, or reads files from a folder the chart doesn't mount. For the others, set the chart's value instead. The chart builds more than the variable on its values, like the permission to impersonate for `auth.mode`, or the probes and the ingress path for `basePath`, while a variable in `extraEnv` changes only Lumovi.

## Where it runs

<ResponseField name="LUMOVI_PORT" type="number" default="8080">
  The port to listen on, from `0` to `65535`. `0` picks any free port, and the log says which. The chart sets it to `8080` itself.
</ResponseField>

<ResponseField name="PORT" type="number">
  The port to listen on when `LUMOVI_PORT` isn't set, as platforms like [Sevalla](/server/fleet/sevalla) set it for the application they run. One that isn't a port stops Lumovi, saying `PORT must be a port number`.
</ResponseField>

<ResponseField name="LUMOVI_ADDRESS" type="string">
  The address to listen on: every interface unless set.
</ResponseField>

<ResponseField name="LUMOVI_URL" type="string">
  The address people open it at, like `https://lumovi.example.com`: an `http` or `https` URL. Single sign-on needs it. With `https:`, cookies are sent over HTTPS only.

  It's also an origin Lumovi accepts sign-ins, sign-outs and pages' connections from, besides the host each request is sent to. Set it when a proxy in front of Lumovi changes the `Host` header. See [Security](/server/security#sessions-and-cookies).
</ResponseField>

<ResponseField name="LUMOVI_BASE_PATH" type="string" default="/">
  Where it is below that address, like `/lumovi`. Each part of the path can have letters, digits, `_`, `.`, `~` and `-`.
</ResponseField>

## The cluster it shows

<ResponseField name="LUMOVI_CLUSTER_NAME" type="string">
  What it calls the cluster: `in-cluster` (or the kubeconfig's context) unless set. In a fleet, the cluster it runs in.
</ResponseField>

<ResponseField name="LUMOVI_CLUSTER_LABELS" type="string">
  The labels of the cluster Lumovi runs in, like `env=production,region=eu-west`: in a fleet, as one of its clusters; on a Lumovi of one cluster, for [AI assistants' rules](/server/assistants#limits-for-everyone) that match clusters by label. Labels that aren't like this stop Lumovi.
</ResponseField>

<ResponseField name="KUBECONFIG" type="string">
  A kubeconfig to show a cluster from, instead of the cluster Lumovi runs in.
</ResponseField>

<ResponseField name="LUMOVI_CONTEXT" type="string">
  The kubeconfig's context to show: its current context unless set. A context the kubeconfig doesn't have stops Lumovi.
</ResponseField>

<ResponseField name="LUMOVI_SERVICE_ACCOUNT_DIR" type="string" default="/var/run/secrets/kubernetes.io/serviceaccount">
  Where the pod's service account token and CA certificate are, inside a cluster. Lumovi needs the token there even when people sign in with their own tokens, and stops without it. In a fleet, it needs them for the cluster it runs in, and to read Secrets. The chart always mounts them.
</ResponseField>

<ResponseField name="KUBERNETES_SERVICE_HOST" type="string">
  Where the API server is, inside a cluster, with `KUBERNETES_SERVICE_PORT`. Kubernetes sets both in every pod: you don't. Without `KUBERNETES_SERVICE_HOST` or `KUBECONFIG`, Lumovi stops, saying it isn't running in a cluster, unless it shows a fleet. In a fleet, it tells Lumovi it runs in a cluster: see `LUMOVI_FLEET_LOCAL`.
</ResponseField>

## A fleet

Many clusters, rather than one: see [A fleet of clusters](/server/fleet). Lumovi shows a fleet when any of `LUMOVI_FLEET_KUBECONFIG`, `LUMOVI_FLEET_KUBECONFIG_FILE`, `LUMOVI_FLEET_SECRETS` and `LUMOVI_FLEET_AGENTS` is set, or `LUMOVI_FLEET_LOCAL` is `true`. It then needs `LUMOVI_AUTH` to be `oidc` or `proxy`, and doesn't use `KUBECONFIG` or `LUMOVI_CONTEXT`. The settings of a fleet's agents are on [Private clusters](/server/fleet/agents#run-it-another-way).

<ResponseField name="LUMOVI_FLEET_KUBECONFIG" type="string">
  A kubeconfig, each of whose contexts is a cluster: YAML or JSON, or that encoded in base64 on one line. Read when Lumovi starts. One that isn't a kubeconfig stops it, saying `LUMOVI_FLEET_KUBECONFIG isn't a kubeconfig: …`, and base64 that isn't YAML says `LUMOVI_FLEET_KUBECONFIG must be YAML, or YAML encoded in base64.`
</ResponseField>

<ResponseField name="LUMOVI_FLEET_KUBECONFIG_FILE" type="string">
  Kubeconfig files, separated by `:`, each of whose contexts is a cluster. Read when Lumovi starts, and again every `LUMOVI_FLEET_REFRESH_SECONDS`. A file that can't be read keeps the clusters it had, and the log says why.
</ResponseField>

<ResponseField name="LUMOVI_FLEET_SECRETS" type="string">
  Secrets of the cluster Lumovi runs in that describe clusters, by whose: `lumovi`, `cluster-api` and `argocd`, separated by commas. Only in a cluster: outside one, and with any other name, Lumovi doesn't start. See [Clusters from Secrets](/server/fleet/discovery).
</ResponseField>

<ResponseField name="LUMOVI_FLEET_SECRETS_NAMESPACES" type="string">
  Where those Secrets are, separated by commas: the service account's namespace unless set.
</ResponseField>

<ResponseField name="LUMOVI_FLEET_AGENTS" type="string">
  The agents that may connect, as a YAML list, or that encoded in base64 on one line: each with a `name`, a `token` of at least 32 characters or its `tokenSha256`, and optional `caSha256` (its cluster's certificate authority's SHA-256, or a list of them), `labels`, `groups` and `forwardToken`. Read when Lumovi starts. See [Private clusters](/server/fleet/agents).
</ResponseField>

<ResponseField name="LUMOVI_FLEET_LOCAL" type="boolean">
  `true` or `false`: whether the cluster Lumovi runs in is one of the fleet's. Unless set, it is whenever Lumovi runs in a cluster and shows a fleet. `true` outside a cluster stops Lumovi, and `true` on its own makes a fleet of just that cluster.
</ResponseField>

<ResponseField name="LUMOVI_FLEET_REFRESH_SECONDS" type="number" default="30">
  How often kubeconfig files and Secrets are read again, in seconds: from 1 to 3600.
</ResponseField>

## Sign-in

<ResponseField name="LUMOVI_AUTH" type="string" default="token">
  `token`, `oidc` or `proxy`. See [Ways to sign in](/server/overview#ways-to-sign-in). A fleet needs `oidc` or `proxy`.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_ISSUER" type="string">
  The OpenID Connect provider's issuer URL, `http` or `https`. Required with `oidc`.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_CLIENT_ID" type="string">
  Lumovi's client ID at the provider. Required with `oidc`.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_CLIENT_SECRET" type="string">
  The client's secret. Unset for a public client.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_SCOPES" type="string" default="openid email profile">
  The scopes to ask for, separated by spaces.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_USERNAME_CLAIM" type="string" default="email">
  The ID token claim that names people.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_GROUPS_CLAIM" type="string" default="groups">
  The ID token claim that lists their groups.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_PROVIDER_NAME" type="string" default="single sign-on">
  The provider's name on the sign-in button: **Sign in with** this.
</ResponseField>

<ResponseField name="LUMOVI_OIDC_FORWARD_TOKEN" type="string">
  `id` or `access`: pass people's own token on (the API server must trust the provider) instead of impersonating them. The token must be a JWT that says when it expires. In a fleet, Lumovi passes it on only to clusters with [`forwardToken: true`](/server/fleet#settings-for-each-cluster), and impersonates people in the others.
</ResponseField>

<ResponseField name="LUMOVI_PROXY_USER_HEADER" type="string" default="X-Forwarded-User">
  The header a proxy names people in. Upper and lower case don't matter.
</ResponseField>

<ResponseField name="LUMOVI_PROXY_GROUPS_HEADER" type="string" default="X-Forwarded-Groups">
  The header a proxy lists their groups in, separated by commas.
</ResponseField>

<ResponseField name="LUMOVI_PROXY_SIGN_OUT_URL" type="string">
  Where signing out of the proxy is: an `http` or `https` URL.
</ResponseField>

<ResponseField name="LUMOVI_USERNAME_PREFIX" type="string">
  Put before impersonated users' names. In a fleet, in every cluster that doesn't have its own.
</ResponseField>

<ResponseField name="LUMOVI_GROUPS_PREFIX" type="string">
  Put before impersonated groups' names. In a fleet, in every cluster that doesn't have its own.
</ResponseField>

<ResponseField name="LUMOVI_SESSION_HOURS" type="number" default="12">
  How long sessions last, in hours: more than 0, at most 168, a week. Behind a proxy, also how long an [AI assistant](/server/assistants) someone allows acts as them.
</ResponseField>

<ResponseField name="LUMOVI_STATE_SECRET" type="string">
  A Secret in the namespace Lumovi runs in, where it keeps sessions, the AI assistants people allowed, and each cluster's settings (read-only, metrics source, node shells), so a restart signs nobody out: see [Across restarts](/server/security#across-restarts). The chart sets it to `<release>-state`, which it makes, with `auth.keepSessions`. Lumovi needs `get` and `patch` on it. Lumovi must run in a cluster for it: outside one, it doesn't start, saying `LUMOVI_STATE_SECRET keeps who’s signed in in the cluster Lumovi runs in, and it isn’t running in one (KUBERNETES_SERVICE_HOST isn’t set).` Nor does it start without `LUMOVI_STATE_KEY`: `LUMOVI_STATE_SECRET needs LUMOVI_STATE_KEY: the key what’s kept is sealed with, from a Secret of its own (the chart makes one).`, or when it can't read the Secret: `Lumovi can’t read Secret lumovi/lumovi-state, where it keeps who’s signed in and the AI assistants they allowed: …`, with why.

  Without it, Lumovi keeps them in `state.json` in `LUMOVI_DATA_DIR`, which only its user can read, sealed with a key in `state.key` beside it, which it makes as it first starts. Without either, in memory, and its log says so, as it starts: `Who’s signed in and the AI assistants they allowed are kept in memory: they’re lost when Lumovi stops.`, then, in a cluster, `The Helm chart’s auth.keepSessions keeps them (LUMOVI_STATE_SECRET).`, or outside one, `Set LUMOVI_DATA_DIR to keep them.` A restart then signs everyone out.
</ResponseField>

<ResponseField name="LUMOVI_STATE_KEY" type="string">
  The key what's kept across restarts is sealed with: at least 32 random characters. With `LUMOVI_STATE_SECRET`, it's needed, from a Secret of its own: the chart sets it from `<release>-state-key`, which it makes, or from `auth.stateKeySecret`. Keep it apart from the state: whoever has both can act as anyone. Shorter, Lumovi doesn't start: `LUMOVI_STATE_KEY must be at least 32 characters, random ones.` Changed, or lost, what was kept doesn't open, and everyone signs in again. Without it, and without `LUMOVI_STATE_SECRET`, Lumovi keeps its own in `state.key` in `LUMOVI_DATA_DIR`, or makes a new one each start, in memory. See [Across restarts](/server/security#across-restarts).
</ResponseField>

<ResponseField name="LUMOVI_HEARTBEAT_SECONDS" type="number" default="30">
  How often pages' connections, and a fleet's agents', are checked, in seconds, at most 3600. Keep it shorter than the idle timeout of the proxies in front of Lumovi. An agent takes two of these and a second without a check for a lost connection, and connects again.
</ResponseField>

## What people can do

<ResponseField name="LUMOVI_READ_ONLY" type="boolean" default="false">
  `true` or `1`: nobody changes anything through Lumovi, in any cluster of a fleet, AI assistants included, and the cluster switcher says "For everyone, on this server". Anything else leaves changes on, and a cluster can be made read-only on the page, for everyone, by Lumovi's admins (or anyone, where there are none): see [Read-only mode](/changes/read-only#in-your-cluster).
</ResponseField>

<ResponseField name="LUMOVI_METRICS_SOURCE" type="string" default="auto">
  Where usage history comes from, unless another source is set for a cluster, for everyone, on the page: `auto`, `off`, or `namespace/service:port`, with a path after it for vmselect (`vm/vmselect:8481/select/0/prometheus`). In a fleet, it's every cluster's.
</ResponseField>

<ResponseField name="LUMOVI_NODE_SHELL" type="string" default="on">
  `on` or `off`: whether people can open [shells on nodes](/debug/node-shell). With `off`, nobody can, in any cluster of a fleet, whatever their RBAC allows: a node's **Shell** tab says **Node shells are off**, and Lumovi refuses to start one, saying `Node shells are turned off on this Lumovi server (LUMOVI_NODE_SHELL=off).` Anything else stops Lumovi, saying `LUMOVI_NODE_SHELL must be on or off, not "…".`
</ResponseField>

<ResponseField name="LUMOVI_NODE_SHELL_NAMESPACE" type="string" default="kube-system">
  Where node shells' pods are created, unless another namespace is set for a cluster, for everyone, on the page: a namespace's name, whose Pod Security must allow privileged pods. In a fleet, it's every cluster's.
</ResponseField>

<ResponseField name="LUMOVI_NODE_SHELL_IMAGE" type="string" default="alpine:3.22">
  The image node shells' pods run, unless another is set for a cluster, for everyone, on the page: one with `sh`, and `nsenter` for shells on the node itself. No spaces, and at most 255 characters. In a fleet, it's every cluster's.

  A namespace that isn't a namespace's name, or an image with spaces, stops Lumovi, saying `LUMOVI_NODE_SHELL_NAMESPACE must be a namespace's name and LUMOVI_NODE_SHELL_IMAGE an image, not "…" and "…".`
</ResponseField>

<ResponseField name="LUMOVI_ALLOW_PRIVATE_CHARTS" type="boolean" default="false">
  `true` or `1`: charts may come from private network addresses.
</ResponseField>

<ResponseField name="LUMOVI_ARTIFACT_HUB_URL" type="string" default="https://artifacthub.io">
  Where to search for charts.
</ResponseField>

<ResponseField name="LUMOVI_VIEWS_DIR" type="string" default="/etc/lumovi/views">
  Where the views and add-ons everyone sees are. The chart sets it itself, to the folder it mounts its `views` value at.
</ResponseField>

<ResponseField name="LUMOVI_HELM" type="string" default="helm">
  The helm to run: `helm` on the `PATH` unless set. The image sets it to `/usr/local/bin/helm`, the helm it comes with.
</ResponseField>

## Access

Who may do what through Lumovi, within what RBAC allows. See [Access for your team](/server/access).

<ResponseField name="LUMOVI_ADMINS" type="string">
  Who sees the **Access** pages and decides who may do what there, separated by commas: groups, exactly as people sign in with them, and people as `user:` and their name, in any case, like `platform-admins,user:ana@example.com`. With none, everyone may do all their RBAC allows.
</ResponseField>

<ResponseField name="LUMOVI_ACCESS" type="string">
  What the server says, which admins see but can't change: a map with `everyone`, `groups`, `profiles`, `grants`, `limits` and `names`, as YAML or JSON, or either encoded in base64 on one line. Lumovi checks it as it starts, and one that doesn't make sense stops it, saying where, like `LUMOVI_ACCESS: limits[0].caps.helm is install, which limits nothing: it’s the most there is.` See [Set it in the chart](/server/access#set-it-in-the-chart).
</ResponseField>

<ResponseField name="LUMOVI_ACCESS_CONFIGMAP" type="string">
  A ConfigMap in the namespace Lumovi runs in, where it keeps what admins set, under `access.json`. The chart sets it to `<release>-access`, which it makes, when `access.admins` names someone. Lumovi needs `get` on it, and `patch` to save what admins change, and stops when it can't read it, or isn't running in a cluster. Without it, `access.json` in `LUMOVI_DATA_DIR`, or memory. See [Where it's kept](/server/access#where-it’s-kept).
</ResponseField>

## AI assistants

See [AI assistants for your team](/server/assistants).

<ResponseField name="LUMOVI_ASSISTANTS" type="string" default="on">
  `on` or `off`: whether AI assistants may sign in and connect, at `mcp` below the base path. With `off`, their addresses answer `404`, saying `This server's administrator has turned AI assistants off.` Anything else stops Lumovi, saying `LUMOVI_ASSISTANTS must be on or off, not "…".`
</ResponseField>

<ResponseField name="LUMOVI_ASSISTANT_RULES" type="string">
  Limits on what everyone's assistants may do, which nothing of theirs loosens: a list of rules, as YAML or JSON, or either encoded in base64 on one line. Each has a `name`, where it applies (`clusters`, `namespaces`), and what it limits (`visibility`, `changes`, `secrets`, `env`, `logs`). One that doesn't make sense stops Lumovi, and its log says which. See [Limits for everyone](/server/assistants#limits-for-everyone).
</ResponseField>

<ResponseField name="LUMOVI_ASSISTANT_CHANGES" type="string">
  Changes as Lumovi 1.4 limited them, kept as limits: `ask` or `never` for every cluster, then clusters' own, by name, separated by commas: `ask,staging=allow,production=never`. `allow` limits nothing: people choose. Unset, people choose everywhere. Anything else stops Lumovi, saying `LUMOVI_ASSISTANT_CHANGES must be ask, allow or never, with clusters' own after it (ask,staging=allow), not "…".` See [What their changes do](/server/assistants#what-their-changes-do).
</ResponseField>

<ResponseField name="LUMOVI_ASSISTANT_RULES_CONFIGMAP" type="string">
  A ConfigMap in the namespace Lumovi runs in, where it keeps each person's own rules for their assistants. The chart sets it to `<release>-assistant-rules`, which it makes. Lumovi needs `get` on it, and `patch` to save people's rules, and doesn't start when it can't read it, or isn't running in a cluster. See [Where people's rules are kept](/server/assistants#where-people’s-rules-are-kept).
</ResponseField>

<ResponseField name="LUMOVI_DATA_DIR" type="string">
  Without `LUMOVI_STATE_SECRET`, a folder where Lumovi keeps who's signed in and the AI assistants they allowed, in `state.json`, sealed with a key in `state.key`, so a restart signs nobody out. Without `LUMOVI_ASSISTANT_RULES_CONFIGMAP`, where it keeps each person's own rules for their assistants, in `assistant-rules.json`. Only Lumovi's user can read either. Without either, it keeps them in memory, and they're gone when it stops. Without `LUMOVI_AUDIT_DIR`, the [audit history](#the-audit-log) is kept in its `audit` folder, and without `LUMOVI_ACCESS_CONFIGMAP`, what [admins set](#access) in `access.json`.
</ResponseField>

<ResponseField name="LUMOVI_ASSISTANT_REDIRECT_HOSTS" type="string">
  Sites, by host name and separated by commas, that an assistant may send people back to over `https` once they allow it: `assistant.example.com`. People's own computers, apps, and VS Code's `vscode.dev` need none. Anything but host names stops Lumovi, saying `LUMOVI_ASSISTANT_REDIRECT_HOSTS must be host names, like assistant.example.com, not "…".` See [Where assistants go back to](/server/assistants#where-assistants-go-back-to).
</ResponseField>

## The audit log

See [Audit log for your team](/server/audit-log). The Helm chart sets the first eight from its [`audit` values](/server/helm-values#the-audit-log). Set the others with `extraEnv`.

<ResponseField name="LUMOVI_AUDIT_LEVEL" type="string" default="access">
  `access` records everything; `changes` records changes, sign-ins, settings and Lumovi's own events, but not shells, port forwards, logs and Secrets read, nor each tool an AI assistant calls. Anything else stops Lumovi, saying `LUMOVI_AUDIT_LEVEL must be changes or access, not "…".` See [How much it records](/server/audit-log#how-much-it-records).
</ResponseField>

<ResponseField name="LUMOVI_AUDITORS" type="string">
  Who sees everyone's events, separated by commas: groups, exactly as people sign in with them, and people as `user:` and their name, in any case, like `platform-admins,user:ana@example.com`. Everyone else sees their own, unless their [access](#access) gives them everyone's. See [Auditors](/server/audit-log#auditors).
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_DIR" type="string">
  The folder for the audit history, a file a day. Unset, the `audit` folder in `LUMOVI_DATA_DIR`, or, without that either, memory: what happened since Lumovi started. See [Where it's kept](/server/audit-log#where-it’s-kept).

  One Lumovi keeps a folder at a time: another that finds it held (`audit.lock` in it) waits for it to be let go, or not renewed for 30 seconds. Still held after about 40 seconds, it doesn't start, saying `Another Lumovi (process … on …) keeps its audit history in …: two can’t, or they’d number events the same. Stop it, or give this one a folder of its own.` Lumovi's user must be able to write there, or it doesn't start either: `LUMOVI_AUDIT_DIR (…) can’t be written in: …`. As it starts, it makes the folder and its files only its own (`0700`, `0600`).
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_RETENTION_DAYS" type="number" default="90">
  How many days the history in `LUMOVI_AUDIT_DIR` keeps, from 1 to 3,650.
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_STDOUT" type="string" default="true">
  `true` or `false`: whether each event is also a line of JSON on Lumovi's output, for the cluster's log collector. See [On the server's output](/server/audit-log#on-the-server’s-output).
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_WEBHOOK_URL" type="string">
  An `http` or `https` URL, in any case, to send each event to, in batches. One that isn't stops Lumovi, saying `LUMOVI_AUDIT_WEBHOOK_URL must be an http or https URL.`, without repeating it, since a URL can hold a token. It can't hold a user and password: Lumovi stops, saying `LUMOVI_AUDIT_WEBHOOK_URL can't carry a user and password: put an Authorization header in LUMOVI_AUDIT_WEBHOOK_HEADERS.` See [To a webhook](/server/audit-log#to-a-webhook).
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_WEBHOOK_FORMAT" type="string" default="json">
  `json`, an array of events in each request, or `ndjson`, a line of JSON each.
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_WEBHOOK_HEADERS" type="string">
  Headers to send with each request, like an `Authorization` header: a map of text, as YAML or JSON, or either encoded in base64 on one line. The chart reads it from the `headers.yaml` of the Secret that `audit.webhook.headersSecret` names. Lumovi checks each as it starts, and says which can't be sent without repeating its value: `LUMOVI_AUDIT_WEBHOOK_HEADERS: Authorization’s value can’t be sent in a header (it has a line break, say).`
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_WEBHOOK_BUFFER" type="number" default="10000">
  How many events wait for the webhook, at most, while it doesn't take them, from 10 to 1,000,000.

  They hold 64 MiB at most, too. Past either, the oldest are let go, and counted. See [To a webhook](/server/audit-log#to-a-webhook).
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_MEMORY_EVENTS" type="number" default="10000">
  Without a folder, how many of the most recent events memory keeps, from 100 to 1,000,000.
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_SCAN_LIMIT" type="number" default="200000">
  How many events one search looks through before it stops, and the page offers to look further back, from 100 to 10,000,000.
</ResponseField>

<ResponseField name="LUMOVI_AUDIT_EXPORT_LIMIT" type="number" default="50000">
  How many events an export holds, at most, from 10 to 1,000,000.
</ResponseField>

The numbers must be whole numbers in their range. Anything else stops Lumovi, saying, for example, `LUMOVI_AUDIT_RETENTION_DAYS must be a whole number from 1 to 3,650, not "…".` So do `LUMOVI_AUDIT_WEBHOOK_HEADERS`, `_FORMAT` or `_BUFFER` without `LUMOVI_AUDIT_WEBHOOK_URL`.

## A company's network

The chart sets these from its `proxy` and `extraCA` values: `proxy.secret` sets the proxies from a Secret. See [Proxies and certificate authorities](/server/network).

<ResponseField name="HTTPS_PROXY" type="string">
  The proxy for `https` addresses, as a URL: `http://proxy.corp.example.com:3128`, with credentials in it if it wants them (`http://user:password@…`). Without a scheme, it's taken as `http://`. `https_proxy` too, when `HTTPS_PROXY` isn't set. One that isn't a URL stops Lumovi: `HTTPS_PROXY isn’t a proxy’s URL: give it as http://host:port (or https://).` Lumovi's own connections go through it: clusters whose kubeconfig names no `proxy-url`, single sign-on, Helm repositories and Artifact Hub, the audit webhook, and an agent's to Lumovi. `localhost`, `127.0.0.1` and `::1` never do, nor, inside a cluster, `KUBERNETES_SERVICE_HOST`, `kubernetes.default.svc`, and names under `.svc` and `.cluster.local`. Lumovi's log says which proxy it uses, without its credentials. `helm` gets it too.
</ResponseField>

<ResponseField name="HTTP_PROXY" type="string">
  The proxy for `http` addresses, the same way. `http_proxy` too.
</ResponseField>

<ResponseField name="NO_PROXY" type="string">
  What's never sent through the proxy, separated by commas or spaces: `*` for all; names, with what's under them (`corp.example.com`, `.corp.example.com`); addresses (`10.1.2.3`), but not ranges; each with a port (`:8443`) or without. `no_proxy` too. Lumovi adds what it never proxies, so `helm` leaves those out as well.
</ResponseField>

<ResponseField name="LUMOVI_CA_FILE" type="string">
  Files of certificate authorities to trust besides Node's and the system's, separated by commas, each with PEM certificates: the one a proxy that inspects HTTPS signs with, say. Lumovi's log says how many it took, and from where. A file that can't be read, has no certificate in it, or one that isn't a certificate, stops Lumovi, saying `The certificate authorities in … can’t be read: …`, `… has no certificates in it (PEM, as -----BEGIN CERTIFICATE-----).`, or `The certificate authorities in … can’t be read: its certificate 2 isn’t one (…).` `helm` trusts them too: Lumovi gives it `SSL_CERT_FILE`, a file with all it trusts, unless `SSL_CERT_FILE` is set already. Clusters trust the certificate authority their kubeconfig names, as with `kubectl`.
</ResponseField>

These work the same as in the desktop app, and the chart has no values for them: set them with `extraEnv`.

## Addresses it answers

All of these are below the base path. Whatever stands in front of Lumovi must pass them all through.

| Address | What it's for |
| --- | --- |
| `GET healthz` | Health checks: answers `200 ok` while Lumovi runs, without signing in. |
| `api/session` | Who's signed in (`GET`), signing in with a token (`POST`, only with token sign-in), and signing out (`DELETE`). |
| `GET auth/sign-in` | Where single sign-on starts: Lumovi sends the browser on to your provider. Only with `oidc`. |
| `auth/callback` | Where your OpenID Connect provider sends people back. Register it as the redirect URI. Only with `oidc`. |
| `api/socket` | Each page's WebSocket. Proxies in front of Lumovi must pass WebSockets here. |
| `api/agent` | Where a fleet's [agents](/server/fleet/agents) connect, with a WebSocket. Only a fleet takes them. |
| `mcp` | Where [AI assistants](/server/assistants) connect (`GET`, `POST` and `DELETE`), with a token Lumovi gave them. |
| `POST oauth/register`, `POST oauth/token`, `POST oauth/revoke` | Where assistants register, get and renew their tokens, and sign out. |
| `GET .well-known/oauth-authorization-server`, `GET .well-known/oauth-protected-resource`, `GET .well-known/oauth-protected-resource/mcp` | How assistants sign in. |
| `authorize` and `api/assistants/authorize` | The page where people allow an assistant, signed in, and what it asks Lumovi. |

Any other address below the base path is Lumovi's page or one of its files, for `GET` and `HEAD`. Other methods get `405`, and other addresses under `api/` and `auth/` get `404`.

Without AI assistants (`LUMOVI_ASSISTANTS=off`), their addresses answer `404`, and the `authorize` page says they're off. Addresses outside the base path get `404`, with a note saying where Lumovi is, except two for AI assistants, which Lumovi answers at the origin's root when it has a base path, like `/lumovi`: `GET /.well-known/oauth-authorization-server/lumovi` and `GET /.well-known/oauth-protected-resource/lumovi/mcp`. See [Below a base path](/server/assistants#below-a-base-path). The base path without its trailing slash, like `/lumovi`, leads to `/lumovi/`.
