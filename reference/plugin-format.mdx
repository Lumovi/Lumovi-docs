A plugin is a YAML file with one document of kind `Plugin`. Its `spec` can hold a place in the sidebar, for a tool whose kinds belong together on one page, and views: under `views:`, a view tells Lumovi how to show a kind. This page lists everything a plugin can say. For a guided introduction, see [Write a plugin](/custom-resources/write-a-plugin) and [Plugins](/custom-resources/plugins).

```yaml certificates.yaml
apiVersion: lumovi.dev/v1beta1
kind: Plugin
metadata:
  name: certificates
spec:
  version: 1.0.0
  needs:
    lumovi: 1.22.0
  groups: [pki.example.com]
  views:
    - kinds:
        - { group: pki.example.com, kind: Certificate }
      icon: shield-check
      columns:
        - { name: Hosts, path: '.spec.dnsNames[*]' }
        - { name: Secret, path: .spec.secretName }
        - { name: Expires, path: .status.notAfter, type: date }
      status:
        - when: { path: '.status.conditions[?(@.type=="Ready")].status', equals: 'True' }
          health: healthy
          label: Ready
        - when: { path: '.status.conditions[?(@.type=="Ready")].status', equals: 'False' }
          health: critical
          label: '{{ .status.conditions[?(@.type=="Ready")].reason ?? "Not ready" }}'
          detail: '{{ .status.conditions[?(@.type=="Ready")].message }}'
      details:
        - { name: Issuer, path: .spec.issuerRef.name }
        - { name: Renews, path: .status.renewalTime, type: date }
      links:
        - name: Secret
          kind: Secret
          objectName: '{{ .spec.secretName }}'
        - name: Issuer
          kind: '{{ .spec.issuerRef.kind ?? "Issuer" }}.pki.example.com'
          objectName: '{{ .spec.issuerRef.name }}'
```

## Files

| | Desktop app | In your cluster |
| --- | --- | --- |
| **Where** | `~/.lumovi/plugins`, or the folder in `LUMOVI_PLUGINS_DIR` | The chart's `plugins` value, mounted at `/etc/lumovi/plugins` |
| **Which files** | Files and links whose names end in `.yaml` or `.yml`, in the folder itself, not in subfolders. A link is followed to the file it points to. Lumovi reads them in order of their names, up to 200, each up to 256 KB. | The same. Kubernetes mounts each entry as a link, which Lumovi follows. |
| **Reloading** | Press <kbd>⌘</kbd><kbd>R</kbd> (Ctrl+R on Windows and Linux) | Change the chart's `plugins` value and upgrade the release |

A file is one plugin: one document. It's used whole or not at all: if anything in it is wrong, none of it is used, and everything wrong with it is listed as a [problem](#problems). Files are read on their own: one with a problem, or one that can't be read, like a link to nothing, doesn't stop the others loading.

## Whose a kind is

A kind is one plugin's. Each kind gets one view, from the one plugin that shows it:

- **Among Lumovi's plugins**, no two show the same kind.
- **A plugin of yours shows the kinds no other plugin has.** If it names a kind one of Lumovi's plugins shows, it isn't used, and the problem says whose kind it is and what to do.
- **To show one of Lumovi's kinds your way, take its plugin's place.** A plugin of yours with the same `metadata.name` as one of Lumovi's, like `flux` or `cert-manager`, is used in its place, all of it: Lumovi's place in the sidebar and every one of its views go, for the kinds yours doesn't show as well. Those get the API server's columns. [Included plugins](/custom-resources/included-plugins) gives each plugin's name.
- **Among your own**, the first by file name is used. A second file with the same name isn't, whatever becomes of the first. Of two that show the same kind, the later isn't: files with the name of one of Lumovi's plugins are settled first, among themselves and against Lumovi's others, and then the rest, each once, in order of their file names.

A group can be shared: three of Lumovi's plugins have kinds in `argoproj.io`. What is one plugin's is the kind. A plugin that shows every kind of a group (`kind: '*'`) has that group to itself, and within a plugin a view for a kind itself wins over one for its whole group.

**API resources** says what shows each kind, under **Shown by**: the plugin's name as the sidebar has it, the name of your file, **Lumovi**, or a dash for a kind nothing shows specially. [All plugins](/custom-resources/plugins#every-plugin-on-one-page) lists every plugin, and says on its row when one of yours is in use in place of one of Lumovi's: **In use in place of Lumovi’s Flux**.

### Kubernetes’ own kinds

A plugin is for a tool's kinds, not Kubernetes' own:

- **A kind Lumovi has a page for**, like Pods, Deployments, Secrets or Roles (see [Resource kinds](/reference/resource-kinds)), can't be in a plugin at all.
- **A kind Lumovi shows itself**, like CustomResourceDefinitions, can't either. Lumovi has views of its own for a few of Kubernetes' kinds that have no page. They aren't plugins and aren't among the [included ones](/custom-resources/included-plugins); **Shown by** says **Lumovi** for them.
- **Any other kind of Kubernetes'**, like a Lease or a LimitRange, a plugin can show, and only show. It names the kind under [`shows`](#spec), and its view of it has columns, status, details, links and related lists, but no actions. Such a kind can't be under the plugin's place in the sidebar.

```yaml limits.yaml
apiVersion: lumovi.dev/v1beta1
kind: Plugin
metadata:
  name: limits
spec:
  version: 1.0.0
  needs:
    lumovi: 1.22.0
  groups: []
  shows:
    - { kind: LimitRange }
  views:
    - kinds:
        - { kind: LimitRange }
      columns:
        - { name: Limits, path: '.spec.limits[*].type' }
```

## The document

<ResponseField name="apiVersion" type="string" required>
  Always `lumovi.dev/v1beta1`.
</ResponseField>

<ResponseField name="kind" type="string" required>
  Always `Plugin`.
</ResponseField>

<ResponseField name="metadata.name" type="string" required>
  The plugin's name: lowercase letters, digits and hyphens, starting with a letter and ending with a letter or a digit, at most 63 characters. It's the address of its page (`plugins/platform`). A name is one plugin's: of two files of yours with the same name, the first by file name is used, and a plugin of yours with the name of one of Lumovi's is used [in its place](#whose-a-kind-is). `lumovi`, a name starting with `lumovi-`, and `kubernetes` can't be a plugin's.
</ResponseField>

<ResponseField name="spec" type="object" required>
  What it says: see [spec](#spec). Any field it doesn't know is a problem, so typos don't go unnoticed.
</ResponseField>

These four are all a document has, and `name` is all its `metadata` has. A key Lumovi doesn't know is a problem wherever it is in the file, so a `metadata.labels` or a stray key at the top isn't passed over in silence.

## spec

A plugin's `spec` holds a place in the sidebar, views, or both. A file with one view and nothing else is a plugin too, the smallest one.

```yaml platform.yaml
apiVersion: lumovi.dev/v1beta1
kind: Plugin
metadata:
  name: platform
spec:
  version: 1.0.0
  needs:
    lumovi: 1.22.0
  groups: [platform.example.com]
  label: Platform
  icon: database
  kinds:
    - { group: platform.example.com, kind: Database }
    - { group: platform.example.com, kind: DatabaseBackup }
  views:
    - kinds:
        - { group: platform.example.com, kind: Database }
      columns:
        - { name: Engine, path: .spec.engine }
```

<ResponseField name="version" type="string" required>
  The plugin's own version: three numbers, like `1.0.0`, with no leading zeros and nothing before or after them. `1.0` and `v1.0.0` are problems.
</ResponseField>

<ResponseField name="needs.lumovi" type="string" required>
  The oldest Lumovi the plugin works with, as three numbers, like `1.22.0`. A plugin that needs a newer Lumovi than the one reading it isn't used, and the problem says both versions.
</ResponseField>

<ResponseField name="groups" type="list of strings" required>
  The API groups its kinds are in, like `[platform.example.com]`. Every kind of a tool's that the plugin names, in its place in the sidebar or in a view, is in one of them. A group is written as Kubernetes writes it: lowercase letters, digits, hyphens and dots. Kubernetes' own groups, like `apps`, and `lumovi.dev` can't be among them. A plugin that only [shows Kubernetes' kinds](#kubernetes’-own-kinds) has an empty list.
</ResponseField>

<ResponseField name="shows" type="list of kinds">
  Kinds of [Kubernetes' own](#kubernetes’-own-kinds) that Lumovi has no page for, which the plugin shows and only shows. Each is written out as a view's [kinds](#a-view) are, with its `group` unless it's of the core group, and each is shown by one of the plugin's views.
</ResponseField>

<ResponseField name="kinds" type="list">
  The kinds of its place in the sidebar, in the order of their tabs: an entry in the sidebar leads to a page with all of them, everything in one list and a tab for each. Written as a view's [kinds](#a-view): `kind: '*'` is every kind of a group, each with a tab, in order of their names. Kubernetes' own kinds can't be among them. See [Plugins](/custom-resources/plugins).
</ResponseField>

<ResponseField name="label" type="string">
  Its name in the sidebar, on its page and in the command palette. Required with `kinds`.
</ResponseField>

<ResponseField name="icon" type="string">
  One of the [icons](#icons). Without one, it gets the puzzle piece of custom resources.
</ResponseField>

<ResponseField name="category" type="string">
  A section of the sidebar for Kubernetes' own kinds to sit in, at its end: `cluster` (**Cluster**), `network` (**Network**), `config` (**Configuration**) or `storage` (**Storage**). Without one, it's under **Plugins**.
</ResponseField>

<ResponseField name="views" type="list of views">
  How its kinds are shown: see [A view](#a-view). A plugin needs views, or `kinds` for a place in the sidebar.
</ResponseField>

A label, an icon and a category are for a place in the sidebar, so they need `kinds`. A place only groups kinds: how each kind looks, its columns, status and actions, comes from a view of this plugin's.

One of yours with the same `metadata.name` as one of Lumovi's is used in its place, all of it: see [Whose a kind is](#whose-a-kind-is).

A few fields are only for the plugins that come with Lumovi: `pages`, `tabs` and `commands`, which add to Lumovi's pages, and `reads` and `showsSecrets`, which say what a plugin's own code may read and show. A file of yours with any of them isn't used, and its [problem](#problems) says which.

## A view

Each item under `views:`:

<ResponseField name="name" type="string">
  A name of its own, if you like. Nothing depends on it.
</ResponseField>

<ResponseField name="kinds" type="list" required>
  The kinds it's for, at least one. Each is a `kind` and its API `group`, and the group is one of the plugin's [`groups`](#spec). A kind's name is its own, like `GitRepository`: letters and digits, starting with a capital, with its group beside it and never in it.

  ```yaml
  kinds:
    - { group: source.toolkit.fluxcd.io, kind: GitRepository }
    - { group: source.toolkit.fluxcd.io, kind: HelmRepository }
  ```

  `kind: '*'` is every kind of a group, like the constraint kinds Gatekeeper makes, one for each of its templates. It needs a `group`. A view for a kind itself wins over one for its whole group.

  ```yaml
  kinds:
    - { group: constraints.gatekeeper.sh, kind: '*' }
  ```

  A kind of Kubernetes' own is left without `group` if it's of the core group, and has to be under the plugin's `shows`: see [Kubernetes' own kinds](#kubernetes’-own-kinds).
</ResponseField>

<ResponseField name="icon" type="string">
  The kind's icon, one of the [icons](#icons) below.
</ResponseField>

<ResponseField name="columns" type="list of fields">
  List columns, shown after the name and status. They replace the columns the API server prints for the kind. See [Fields](#fields).
</ResponseField>

<ResponseField name="status" type="list of rules">
  How to tell whether an object is healthy. The first rule that applies decides. With no rule that applies, Lumovi reads the status from [the usual conventions](/custom-resources/overview#status). See [Status rules](#status-rules).
</ResponseField>

<ResponseField name="details" type="list of fields">
  Facts in the detail panel's **Details** section. See [Fields](#fields).
</ResponseField>

<ResponseField name="links" type="list of links">
  Single objects this one points to, listed under **Related** in the detail panel's **Overview**. See [Links](#links).
</ResponseField>

<ResponseField name="related" type="list of related lists">
  Objects of other kinds that belong to this one, a tab each in the detail panel. See [Related](#related).
</ResponseField>

<ResponseField name="actions" type="list of actions">
  Changes people can make: a patch of the object, or a new object to create. See [Actions](#actions).
</ResponseField>

<ResponseField name="manages" type="list">
  How an object of this kind marks the workloads it manages, so a workload says what manages it. See [What it manages](#what-it-manages).
</ResponseField>

## Paths

Paths are the part of kubectl's JSONPath that CRD printer columns use, starting with a dot.

| Path | Finds |
| --- | --- |
| `.spec.secretName` | A field |
| `.metadata.labels['app.kubernetes.io/name']` | A key with dots or slashes (or `labels.app\.kubernetes\.io/name`) |
| `.spec.containers[0].image`, `[-1]` | An item of a list, counting from the end when negative |
| `.spec.hosts[*]`, `.metadata.labels.*` | Every item of a list, or every value of a map |
| `.status.conditions[?(@.type=="Ready")].status` | Items that match: `==` or `!=` a string, number, `true`, `false` or `null` |
| `.spec.parts[?(@.spare)]` | Items where a field is set (and not false) |

A path can also be written `{.spec.x}` or `$.spec.x`. When a path finds several values, they're shown joined with commas.

<Tip>
  In YAML, quote paths that contain brackets or double quotes, and anything that starts with `{`: `'.status.conditions[?(@.type=="Ready")].status'`.
</Tip>

## Conditions

A condition reads one value at `path`, and compares it:

```yaml
when: { path: .status.phase, equals: Running }             # or notEquals
when: { path: .status.phase, in: [Failed, Error] }
when: { path: .status.message, matches: 'timeout|refused' } # a regular expression, ignoring case
when: { path: .spec.suspend, exists: true }                 # or false
when: { path: .spec.suspend }                               # set, and not false, 0 or empty
```

| Operator | Holds when the value |
| --- | --- |
| `equals` | Is this string, number, boolean or null |
| `notEquals` | Isn't |
| `in` | Is any of these (a list, not empty) |
| `matches` | Matches this regular expression, ignoring case |
| `exists` | Is set (`true`), or isn't (`false`) |
| (none) | Is set, and not false, 0 or empty |

Comparisons ignore case, so `equals: True` matches Kubernetes' `"True"` even though YAML reads an unquoted `True` as a boolean. When a path finds several values, the first is compared. A condition with more than one operator uses the first of `exists`, `equals`, `notEquals`, `in` and `matches` that it has.

Conditions combine with `all` and `any`, nested as deep as you need:

```yaml
when:
  all:
    - { path: .spec.suspend, notEquals: true }
    - any:
        - { path: .status.phase, equals: Running }
        - { path: .status.phase, equals: Succeeded }
```

A condition has exactly one of `path`, `all` or `any`.

## Templates

A status rule's `label` and `detail`, links, related lists, and actions' texts, patches and new objects can include values from the object.

| Template | Gives |
| --- | --- |
| `{{ .path }}` | The value at a path; several are joined with commas |
| `{{ .spec.issuerRef.kind ?? "Issuer" }}` | The value, or this text when the path finds nothing |
| `{{ .spec.target.name ?? .metadata.name }}` | The value, or another path's |
| `{{ now }}` | The current time, as Kubernetes writes times (most useful in patches) |
| `{{ input.replicas }}` | What was given for one of an action's [inputs](#inputs). One left empty counts as nothing, so `??` works on it. |

### In patches and new objects

In a `patch`, an `undo` or an object to `create`, a value that's a template and nothing else stands for the value itself, not its text:

- A number stays a number, and a list or an object is copied whole: `params: '{{ .spec.params }}'` copies the object's parameters.
- When the template finds nothing, the field is left out (and a list item is dropped), rather than set to an empty string.
- `{{ now }}` is always text, and so is everything under `labels` and `annotations`, which Kubernetes keeps as text.

A value with other text around its template, like `'{{ .metadata.name }}-copy'`, is always text.

Templates in `undo` are filled in from the object as it was before the action ran. So an undo can put back the value an action replaces: `undo: { spec: { mode: '{{ .spec.mode }}' } }`.

## Related

Related lists are the objects of another kind that belong to this one: a node pool's nodes, a database's instances, a pipeline's runs. Each is a tab of the detail panel, after **Metrics**, listing them with their kind's usual columns. They're also on the object's **Map**.

```yaml
related:
  - name: Instances
    kind: Pod
    labels: { cnpg.io/cluster: '{{ .metadata.name }}', cnpg.io/podRole: instance }
  - name: Nodes
    kind: Node
    labels: { karpenter.sh/nodepool: '{{ .metadata.name }}' }
```

<ResponseField name="name" type="string" required>
  The tab's name, like `Instances` or `Nodes`.
</ResponseField>

<ResponseField name="kind" type="template" required>
  Their kind, named as for [links](#links): `Pod`, `NodeClaim.karpenter.sh`.
</ResponseField>

<ResponseField name="labels" type="map of templates">
  The labels they have, each value a template: `cnpg.io/cluster: '{{ .metadata.name }}'`.
</ResponseField>

<ResponseField name="fieldSelector" type="template">
  A field selector they match, like `'spec.nodeName={{ .status.nodeName }}'`.
</ResponseField>

<ResponseField name="namespace" type="template">
  Where to look. This object's namespace unless set. Kinds without namespaces are looked for across the cluster, and so is everything related to an object that has no namespace.
</ResponseField>

A related list needs `labels` or a `fieldSelector`: without one, it would be every object of the kind. A list whose kind, label values or field selector values come out empty isn't shown, since it would find the wrong objects. Like any list, it needs `list` on the kind.

The first list of `Pod`s is special: it becomes the panel's **Pods** tab, under the list's name (CloudNativePG's **Instances**). It brings a **Logs** tab with their logs, merged, and a **Metrics** tab with their [usage history](/metrics/usage-history).

## What it manages

A tool that deploys workloads, like a GitOps tool, marks each one it deployed with labels or annotations of its own. A view's `manages` says which, so Lumovi can tell a workload's manager: workloads' lists get a **Managed by** column, and a workload's **Overview** starts with a line for each manager, like "Kustomization flux-system/apps manages this deployment, and may undo changes made to it any other way.", which opens it.

```yaml
views:
  - kinds: [{ group: kustomize.toolkit.fluxcd.io, kind: Kustomization }]
    manages:
      - labels:
          kustomize.toolkit.fluxcd.io/name: '{{ .metadata.name }}'
          kustomize.toolkit.fluxcd.io/namespace: '{{ .metadata.namespace }}'
```

Each item holds `labels`, `annotations` or both: the keys a managed workload carries, each with a [template](#templates) of the manager's. A workload is managed by an object of this kind when every key of one item is on it, with exactly the value the template gives for that object. A template may also name the managed workload itself, as `{{ object.group }}`, `{{ object.kind }}`, `{{ object.namespace }}` and `{{ object.name }}`, for a tool that writes a workload's own name into its mark:

```yaml
manages:
  - annotations:
      argocd.argoproj.io/tracking-id: '{{ .metadata.name }}:{{ object.group }}/{{ object.kind }}:{{ object.namespace }}/{{ object.name }}'
```

- **At most 4 items**, and 8 keys in one.
- **Each key is under the group of the view's kinds**, or one under it: `kustomize.toolkit.fluxcd.io/name` for a Kustomization, `argocd.argoproj.io/tracking-id` for an Argo CD Application (`argoproj.io`). Never one of Kubernetes' own (`kubernetes.io`, `k8s.io` and every name under them), nor a key with no group: any chart can set those, so they can't tell one tool's workloads from another's.
- **Only for kinds of its own**, named one by one: a view of one of Kubernetes' own kinds only shows it, and `kind: '*'` can't say what it manages.
- The workloads are Deployments, StatefulSets, DaemonSets, Jobs and CronJobs.

To find managers, Lumovi lists each such kind in the whole cluster where you may list it, or else in the namespaces you're looking at, as you. The [Plugins page](/custom-resources/plugins#what-a-plugin-asks-for) says so for each plugin. Where no plugin says what it manages, nothing more is read.

## Actions

Actions change the object with a patch, like `kubectl patch`, or create another object, like `kubectl create`. Each has a `patch` or a `create`, not both.

```yaml
actions:
  - name: Reconcile
    icon: refresh-cw
    primary: true                                  # a button in the detail panel, not only in its menu
    when: { path: .spec.suspend, notEquals: true } # only offered when this holds
    runs: at-once                                  # it asks nothing first, and says so
    patch:
      metadata:
        annotations: { reconcile.fluxcd.io/requestedAt: '{{ now }}' }
    done: Asked Flux to reconcile {{ .metadata.name }} # the notification

  - name: Suspend
    runs: at-once
    patch: { spec: { suspend: true } }
    undo: { spec: { suspend: null } }              # offered as Undo in the notification
    done: Suspended {{ .metadata.name }}

  - name: Abort
    danger: true
    confirm: The rollout stops and traffic goes back to the stable version. # asks first
    subresource: status                            # patches the status subresource
    patch: { status: { abort: true } }
```

<ResponseField name="name" type="string" required>
  The action's name, in menus and on its button.
</ResponseField>

<ResponseField name="patch" type="object or list">
  A merge patch (an object), or, with `type: json`, a list of JSON patch operations. Templates work inside it, within [what a patch can't change](#what-a-patch-can’t-change).
</ResponseField>

<ResponseField name="create" type="object">
  An object to create instead, with templates. See [Creating objects](#creating-objects).
</ResponseField>

<ResponseField name="inputs" type="list of inputs">
  Values to ask for before it runs, at least one. See [Inputs](#inputs).
</ResponseField>

<ResponseField name="type" type="string" default="merge">
  `merge` or `json`. A merge patch is an object, and a JSON patch is a list; anything else is a problem.
</ResponseField>

<ResponseField name="subresource" type="string">
  `status`, to patch the object's status subresource.
</ResponseField>

<ResponseField name="undo" type="object or list">
  A patch that takes the change back, offered as **Undo** in the notification. Same type as `patch`, and filled in from the object as it was before. Actions that create have no undo.
</ResponseField>

<ResponseField name="confirm" type="template">
  Asks first, with this text.
</ResponseField>

<ResponseField name="runs" type="string">
  `at-once`, on an action that asks nothing first. See [When an action asks first](#when-an-action-asks-first).
</ResponseField>

<ResponseField name="done" type="template">
  The notification once it's done. Without it, the notification is the action's name and the object's.
</ResponseField>

<ResponseField name="when" type="condition">
  Offer the action only when this holds.
</ResponseField>

<ResponseField name="primary" type="boolean">
  Also show it as a button in the detail panel, not only in its menu.
</ResponseField>

<ResponseField name="danger" type="boolean">
  It's destructive: it's shown in red, and its confirmation starts on **Cancel**.
</ResponseField>

<ResponseField name="icon" type="string">
  One of the [icons](#icons). Without one, an action gets a lightning bolt.
</ResponseField>

### When an action asks first

An action with a `confirm`, `inputs` or a `create` opens a dialog first, and its name ends in "…" in menus, like **Back up now…**. The dialog shows the `confirm` text, the inputs, what it would create, and the equivalent command. Its button has the action's name.

An action with none of the three runs at once, and has to say so: `runs: at-once`. That way nobody reading the file takes a change that asks nothing for one that asks. An action that asks first can't say it.

### What a patch can’t change

Some of an object's `metadata` is the cluster's to set, or its owner's, and no plugin's:

- **In a patch or an undo:** `ownerReferences`, `finalizers`, `managedFields`, `namespace`, `name`, `uid`, `resourceVersion`, `generation`, `creationTimestamp` and `deletionTimestamp`.
- **In an object to create:** `ownerReferences`, `finalizers` and `managedFields`. A new object has its name, and can have a namespace.

So that nothing filled in later can get round this, a few things are written out and never come from a template:

- `metadata`, in a patch or an object to create, is a map written in the file, not one placeholder.
- Each operation of a JSON patch is written out, and so are its `path` and `from`, as text with no `{{ }}` in them.
- A JSON patch operation can't name `/metadata` itself or the whole object, and can't name one of the fields above in its `path` or `from`, whatever the operation is.

Labels and annotations are yours to set, and their values can be templates.

The file is checked when it's read. The change is checked again as it's sent, filled in: one that would change any of these isn't sent, and the notification says "Lumovi didn’t send this: it changes metadata.finalizers, which a plugin can’t change."

### Inputs

Inputs are values an action asks for, used in its templates as `{{ input.name }}`.

```yaml
- name: Switch over
  inputs:
    - name: instance
      label: New primary
      type: choice
      from: '.status.instanceNames[*]'
  confirm: The instance chosen becomes the primary, and {{ .status.currentPrimary }} a replica.
  subresource: status
  patch: { status: { targetPrimary: '{{ input.instance }}' } }
  done: Switching {{ .metadata.name }} over to {{ input.instance }}

- name: Pause at
  inputs:
    - { name: replicas, label: Replicas while paused, type: number, default: '{{ .status.originalReplicaCount }}' }
  patch:
    metadata:
      annotations: { autoscaling.keda.sh/paused-replicas: '{{ input.replicas }}' }
```

<ResponseField name="name" type="string" required>
  How templates name it: letters, digits and `_`, not starting with a digit, like `replicas`.
</ResponseField>

<ResponseField name="label" type="string" required>
  What the dialog calls it.
</ResponseField>

<ResponseField name="type" type="string" default="text">
  - `text`: a text field.
  - `number`: a whole number from 0 to 1,000. In a patch, a template that's only this input gives a number (except under `labels` and `annotations`).
  - `choice`: one of a few options, picked from a list.
</ResponseField>

<ResponseField name="options" type="list">
  A choice's options: `[Off, Initial, Recreate]`.
</ResponseField>

<ResponseField name="from" type="path">
  Where to read a choice's options from instead, like `'.status.instanceNames[*]'`. When it finds nothing, the dialog says **There's nothing to choose from.**
</ResponseField>

<ResponseField name="default" type="template">
  The value it starts with. Without one, a number starts at 0, and a choice on its first option.
</ResponseField>

A choice has `options` or `from`, not both, and other inputs have neither. Every input needs a value before the action can run. Templates in `patch`, `create`, `confirm` and `done` can only name inputs the action has.

### Creating objects

`create` is an object to create, written as you'd write its YAML, with templates in it. It needs an `apiVersion`, a `kind`, and a `metadata.name` or `metadata.generateName` as text. What it creates is one of the plugin's own kinds: one under its place in the sidebar, or one a view of it shows. So its `apiVersion` and `kind` are written out, not templates.

```yaml
- name: Back up now
  icon: archive
  inputs:
    - { name: method, label: Method, type: choice, options: [barmanObjectStore, volumeSnapshot] }
  create:
    apiVersion: postgresql.cnpg.io/v1
    kind: Backup
    metadata:
      generateName: '{{ .metadata.name }}-'
    spec:
      cluster: { name: '{{ .metadata.name }}' }
      method: '{{ input.method }}'
  done: Started a backup of {{ .metadata.name }}
```

- **Its name.** With `generateName`, Lumovi picks the random end of the name itself, the way the API server would, so the dialog shows the name it will get.
- **Its namespace.** The object's own, unless `metadata.namespace` says otherwise. Kinds without namespaces get none.
- **Copying.** A template that's a whole value copies it, lists and objects included, and leaves the field out when it finds nothing. Tekton's **Run again** copies a run's pipeline, parameters and workspaces this way: `params: '{{ .spec.params }}'`.
- **Before and after.** The dialog shows the object as YAML first, under **Creates** with its kind and name. Once it's created, **Open** in the notification opens it.

Creating something can't be undone from the notification: delete what it made instead.

### Permissions and commands

An action is enabled only when the cluster says your account may make the change: `patch` on the kind (or on its `status`, with `subresource: status`) for a patch, and `create` on the kind it creates for a `create`. Like every change, it shows the equivalent command, `kubectl patch …` or `kubectl create -f <name>.yaml`, and is refused in a [read-only](/changes/read-only) cluster.

## Texts

A plugin's own texts are plain text, and short enough to show:

- **80 characters at most** for a `name`, a `label` and an input's `default`.
- **500 characters at most** for a `confirm`, a `detail` and a `done`, and for a status rule's `label`, which is a template.
- **No characters that can't be seen**, in any text or key of the file: the ones that turn a text's direction, the ones with no width, and control characters. A `name`, a `label` and a `default` can't hold a line break or a tab either. The problem names the character by its code point, like U+202E.

What a patch or a created object holds is the cluster's to limit, so the two lengths don't apply inside `patch`, `undo` and `create`.

A file that isn't valid YAML shows the parser's message. One that can't be read as YAML for any other reason is listed as one that couldn't be read, with the reason, and the others load.

When a plugin of yours with a problem has the name of one of Lumovi's, Lumovi's is what's shown, and the file's row says so: **Lumovi’s Flux is shown instead**. It's said only where the file's name for itself could be read.

**API resources** says only that there are problems, **A plugin couldn’t be used.** or how many, with **See Plugins**; and at its foot how many plugins are Lumovi's and how many are yours, and where yours go, with **How to write a plugin**.
