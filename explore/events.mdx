Kubernetes records an event when something happens to an object: a pod is scheduled, an image fails to pull, a probe fails, a node runs low on memory. **Events** lists them, newest first. Open it from the sidebar under **Cluster**, with <kbd>G</kbd> then <kbd>E</kbd>, or with <kbd>⌘</kbd><kbd>6</kbd> in the desktop app (<kbd>Ctrl</kbd><kbd>6</kbd> on Windows and Linux).

| Column | Shows |
| --- | --- |
| **Type** | <span className="lumovi-status warning">Warning</span> or <span className="lumovi-status neutral">Normal</span> |
| **Reason** | A short code, like `BackOff`, `FailedScheduling` or `Pulled` |
| **Object** | The object it's about, like `Pod/checkout-7d9f…`. Click it to open that object. |
| **Message** | What happened, in words |
| **Count** | How many times it happened |
| **Last seen** | When it last happened |

## Only the warnings

The chips above the list count each type. Pick **Warning** to hide the routine events. The overview's **Warnings** tile opens the list this way.

The filter (<kbd>/</kbd>) matches an event's reason, message and object name as well as its labels, so typing `OOMKilled` or a pod's name finds what you're after.

## An object's own events

Every object's detail panel has an **Events** tab with the events about it, newest first. It's often the fastest way to see why a pod won't start or a volume won't bind. The overview lists the latest warnings across the namespace, too.

<Note>
  Kubernetes keeps events for a limited time (an hour, unless the cluster is set up otherwise), so old ones disappear. For a longer view of what a workload did, see [Usage history](/metrics/usage-history) and its logs.
</Note>
