**Nodes** lists the machines in the cluster, with the ones in trouble first. Open it from the sidebar under **Cluster**, with <kbd>G</kbd> then <kbd>N</kbd>, or with <kbd>⌘</kbd><kbd>5</kbd> in the desktop app (<kbd>Ctrl</kbd><kbd>5</kbd> on Windows and Linux). Nodes aren't in a namespace, so the list always shows all of them.

## The list

| Column | Shows |
| --- | --- |
| **Status** | Whether the node is ready, and anything wrong with it |
| **Roles** | Its roles, like `control-plane` |
| **CPU**, **Memory** | Meters of live use against what the node can give its pods. Without [metrics-server](/metrics/live-usage), the node's allocatable capacity. |
| **Version** | The kubelet's Kubernetes version |
| **Age** | How long ago it joined |

A node's status is one of:

| Status | Means |
| --- | --- |
| <span className="lumovi-status healthy">Ready</span> | It's ready, with no pressure and nothing turned off. |
| <span className="lumovi-status critical">NotReady</span> | Its `Ready` condition isn't `True`: the node isn't healthy, or has stopped reporting. |
| <span className="lumovi-status warning">MemoryPressure</span> | Another of its conditions is `True`, and the label names it, like `MemoryPressure`, `DiskPressure` or `PIDPressure`. |
| <span className="lumovi-status warning">Cordoned</span> | It's marked unschedulable, so no new pods go there. |

## Open a node

**Overview** has:

- **Details**: its internal IP, OS image, kernel, container runtime, kubelet version, architecture, pod CIDR, and whether it's **Schedulable**.
- **Capacity**: CPU and memory in use against what's allocatable, and how many pods can be scheduled on it.
- **Taints**, when it has any.
- **Conditions**, labels and annotations.

**Pods** lists every pod running on the node, from every namespace, failing ones first. **Metrics** charts its CPU and memory over time against its capacity, when Lumovi has found your [usage history](/metrics/usage-history). **Map** shows the pods that run on it and what runs them. See [Map](/explore/map). **Events** and **YAML** are there as for any object. A node has no **Logs** tab: that would be everything on it.

## A shell on the node

**Shell**, at the top of the panel, opens the node's **Shell** tab. From there, Lumovi starts a short-lived privileged pod on the node and opens a shell through it: as root on the node itself, or in the pod, with the node's files under `/host`. Nothing starts until you choose **Start shell**, and the pod is deleted when the shell ends. Your RBAC, and the Pod Security of the namespace the pod runs in, decide whether you can. See [Shells on nodes](/debug/node-shell).

## Take a node out of service

| Action | What it does |
| --- | --- |
| **Cordon** | Marks the node unschedulable. Pods on it keep running, and no new ones arrive. Undo it from the notification. |
| **Uncordon** | Makes it schedulable again. |
| **Drain…** | Cordons it, then evicts its pods so they're rescheduled elsewhere. |
| **Taints…** | Adds and removes its taints, which keep pods off it unless they tolerate them. |

A drain takes `kubectl drain`'s options:

- **Grace period**: how long each pod has to stop before it's killed, at least 1 second. By default, each pod's own `terminationGracePeriodSeconds` (`--grace-period`).
- **Give up after**: how long to keep trying pods a PodDisruptionBudget holds. Then those pods stay, and so does the cordon (`--timeout`).
- **Delete emptyDir data**, for pods with `emptyDir` volumes, whose data is lost (`--delete-emptydir-data`).
- **Leave DaemonSet pods**, on by default: their DaemonSet would start them here again anyway. Off, a DaemonSet pod stops the drain (`--ignore-daemonsets`).
- **Evict pods without a controller**, for pods that nothing will recreate (`--force`).

Static pods stay where they are: the kubelet manages them. **Drain** stays disabled until the options the node's pods need are ticked. Evictions respect PodDisruptionBudgets: a pod a budget holds is tried again whenever its budgets allow, its row saying which budget and why, until the drain gives up or you stop it. Then the dialog says which pods it stopped on, like "Stopped after 5:00: 2 pods are still on worker-2, held by PodDisruptionBudgets. It stays cordoned." In a cluster named like production, you type the node's name first.

## Taints

**Taints…** lists the node's taints, and adds and removes them. A taint keeps pods off the node unless they tolerate it, by its effect:

| Effect | What it does |
| --- | --- |
| `NoSchedule` | No new pod lands here unless it tolerates the taint. Pods already running stay |
| `PreferNoSchedule` | The scheduler avoids the node, but may still use it |
| `NoExecute` | As `NoSchedule`, and pods already running that don't tolerate it are evicted at once |

Remove a taint with its **Remove** button, and **Keep** to take that back; add one with a key, an optional value and an effect. Nothing changes until **Apply**. Taints Kubernetes sets itself, like a node that isn't ready, say **Set by Kubernetes**, and removing the control plane's says that pods will then be scheduled on it.

Where a `NoExecute` taint is staged, the dialog says first which pods it evicts at once, like "Applying this evicts 3 pods from worker-2 at once.", and its button says so: **Apply and evict 3 pods**. Undo, in the notification, puts the taints back; pods it evicted don't come back.

Apply sends one change that touches only the taints you added or removed, each removal checked against the taint as Lumovi read it. If the node's taints changed while the dialog was open, nothing is changed, and it shows them as they are now, with your changes still staged. The command beside it does the same with `kubectl taint`, and the [audit log](/audit/events) records it as `resource.patch`, like "Tainted worker-2 with dedicated=gpu:NoSchedule" or "Changed worker-2’s taints: dedicated=gpu:NoSchedule added, maintenance:NoExecute removed".
