When logs aren't enough, get inside. Lumovi opens a terminal in a running container, like `kubectl exec -it`, right in the pod's panel. For images with no shell at all, it adds a debug container that brings its own tools, like `kubectl debug`.

For a problem on the node under a container, a node has a **Shell** tab too: see [Shells on nodes](/debug/node-shell).

## Open a shell

<Steps>
  <Step title="Open a running pod">
    Find the pod in **Pods**, or in a workload's **Pods** tab, and open it.
  </Step>
  <Step title="Choose Shell">
    Choose **Shell** at the top of the panel, or open the **Shell** tab.
  </Step>
  <Step title="Pick the container">
    The terminal connects to the pod's first container. Pick another from the container menu; debug containers you've added are listed too.
  </Step>
</Steps>

Lumovi starts `bash` when the container has it, and `sh` otherwise. There's nothing to choose:

```bash
sh -c 'command -v bash >/dev/null 2>&1 && exec bash || exec sh'
```

## In the terminal

- The terminal fits the panel, and the container learns its new size when you resize the panel. Expand the panel for more room.
- It keeps 10,000 lines of scrollback, and uses the app's colors in light and dark.
- Keys go to the terminal: <kbd>Esc</kbd> works in `vi` and `less`, and doesn't close the panel.
- **Reconnect** starts a fresh session in the same container.

## When it ends

The session ends when the shell exits, when the connection to the container closes, or when you close the tab, open something else or quit. The terminal says why:

| Message | Means |
| --- | --- |
| The shell exited with code N. | You exited, or the shell did. |
| The connection to the container closed. | The container stopped, or the network dropped. |
| _container_ has no shell. | The image has neither `bash` nor `sh`. Choose **Debug** to add a debug container instead. |

**Reconnect** starts again either way.

The [audit log](/audit/overview) records each shell you open and close, how long it ran, and how it ended: not what you typed.

## Attach to its main process

A shell is a new process beside the container's own. To reach the container's own process instead, as `kubectl attach -it` does, choose **Attach** in a pod's actions, or **Shell | Attach** on its Shell tab. What the process prints shows in the terminal, and, where its input is open, what you type goes to it. Close the tab to leave: that detaches, and the process goes on.

  <img className="hidden dark:block" loading="lazy" src="https://cdn.jsdelivr.net/gh/Lumovi/Lumovi@main/docs/screenshots/attach-dark-1x.webp" alt="Attached to a container's main process, as kubectl attach -it: what it prints, and what you type where it takes input." />
</Frame>

Lumovi reads the container's spec first, and says at the top of the terminal what attaching does there:

| The container | The terminal says | What you type |
| --- | --- | --- |
| `stdin: true` | “What you type goes to _c_'s main process, Ctrl+C and Ctrl+D included, which can end it. To leave it running, close this.” | Goes to the process |
| `stdin: true` and `stdinOnce: true` | “_c_'s input closes when one session ends, which would end its process: this shows what it prints, and sends it nothing.” | Goes nowhere |
| No `stdin` | “_c_ takes no input (its stdin isn't open): this shows what it prints.” | Goes nowhere |

<Warning>
  Attached, <kbd>Ctrl</kbd><kbd>C</kbd> is the process's, not the terminal's: it stops what's running in the container, and the container may restart. <kbd>Ctrl</kbd><kbd>D</kbd> ends the input of most programs that read it. To leave, close the tab.
</Warning>

Attaching is allowed where shells are: your [access](/clusters/your-access) on a server, `create` on `pods/attach` in the namespace, and not on a [read-only](/changes/read-only) cluster ("production is read-only in Lumovi, so attaching, which sends what you type to a container's process, is turned off."). Where it isn't, the tab says **You can't attach to containers here**, **Attaching is off** or **No attach access**, as a shell's does, and a container that isn't running says "You can attach once the container runs." The [audit log](/audit/events) records each attach and detach, with the command and whether what you typed went to the process: "Attached to Pod console (repl)", "Detached from Pod console (repl), after 2m". Never what you typed.

## When a shell isn't offered

| You see | Why | What to do |
| --- | --- | --- |
| **You can't open shells here** | On a Lumovi server, your [access](/clusters/your-access) doesn't let you open shells in the namespace. It says why, and who Lumovi's admins are. | **See your access**, or ask an admin. |
| **Shells are off** | The cluster is [read-only](/changes/read-only) in Lumovi. A shell can change a container. | Allow changes to the cluster, if you mean to. |
| **No shell access** | Your account can't open shells in the namespace. | Ask for `create` on `pods/exec`. See [Permissions](/clusters/permissions). |
| _container_ **isn't running** | A shell needs a running container. | Wait for it to start, or check its logs and events. |

## Debug containers

Distroless and scratch images have no shell, and many slim images have no tools. A debug container fixes both: Lumovi adds a temporary container with the tools you pick to the running pod, and opens a shell in it. The pod's own containers aren't restarted.

On a Lumovi server, a debug container needs your [access](/clusters/your-access) to let you open shells and make changes in the pod's namespace.

<Steps>
  <Step title="Choose Debug…">
    Open a running pod, and choose **Debug…** from its actions. Or choose **Debug** where a shell says the container has none.
  </Step>
  <Step title="Pick an image">
    | Image | Brings |
    | --- | --- |
    | `busybox:1.37` (the default) | Small: sh, ps, top, wget, nslookup |
    | `nicolaka/netshoot:v0.14` | Networking: curl, dig, tcpdump, iperf and more |
    | `alpine:3.22` | apk, to install what you need |
    | Other image | Any image you name, like `ubuntu:24.04` |
  </Step>
  <Step title="Choose whose processes to share">
    **Share processes with** a container to see its processes from the debug container, with `ps`, and reach its files through `/proc`. It starts on the pod's first container. Choose **no container** to keep them apart.
  </Step>
  <Step title="Start debugging">
    Choose **Start debugging**. Lumovi adds a container named `debugger-` and five random characters, and opens a shell in it, in the pod's **Shell** tab.
  </Step>
</Steps>

The equivalent command is shown before you start:

```bash
kubectl debug -it web-1 --image=busybox:1.37 --container=debugger-ab12c --target=web -n shop --context dev
```

<Note>
  A debug container is an ephemeral container: it stays in the pod until the pod is replaced, and can't be removed before then. Adding one needs `patch` on `pods/ephemeralcontainers`, and like other changes, it's off in read-only clusters.
</Note>

For a shell on your own computer, with kubectl pointed at the cluster, see [Terminals](/debug/terminal).
