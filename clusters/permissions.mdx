Lumovi acts with your credentials: the ones in your kubeconfig on the desktop, or the identity you signed in with when it runs [in your cluster](/server/overview). It never has more access than you do, and it doesn't need cluster-admin. An account that can only read a few namespaces works fine.

In a [fleet](/server/fleet), each cluster applies your RBAC there: Lumovi impersonates you with credentials that may do nothing else, or passes your own token on. What you may do can differ from one cluster to the next. For whoever runs the fleet: in each cluster, Lumovi's own credentials need nothing but `impersonate` on users and groups. See [Add a cluster](/server/fleet/members).

## Asked up front

Before it offers a change, Lumovi asks the cluster whether you're allowed to make it, with a [SelfSubjectAccessReview](https://kubernetes.io/docs/reference/access-authn-authz/authorization/#checking-api-access) per action (the same check as `kubectl auth can-i`). Kubernetes lets every signed-in account make these checks.

- An action you can't take stays visible, but disabled, and says why: *Your account can't delete pods in shop.*
- If the cluster can't say, the action stays available and the API server has the final word.
- Answers are kept for five minutes.

A cluster you made [read-only](/changes/read-only) disables every change regardless, with *Changes are turned off for this cluster.*

## Looking around

Lists and details need `list` and `get` on the kinds you look at. Lumovi refreshes lists by asking again every few seconds (less often for long lists), so it doesn't need `watch`.

| To see | Needs |
| --- | --- |
| A list, and an object's details | `list` and `get` on that kind |
| The namespace menu | `list` on `namespaces`. Without it, type a namespace's name. |
| The overview | `list` on nodes, pods, workloads and events |
| Live CPU and memory | `list` on `pods` and `nodes` in the `metrics.k8s.io` group |
| Logs | `get` on `pods/log` |
| Custom resources | API discovery, which every account can read, and `list` on the kinds |
| A cluster's card in a [fleet](/clusters/fleet) | `list` on nodes, pods, Deployments, StatefulSets, DaemonSets and events across that cluster, and node metrics for CPU and memory. A figure you can't list says **No access**. |
| **Find a workload** in a fleet | `list` on Deployments, StatefulSets, DaemonSets and CronJobs across each cluster |
| An add-on's page | `list` on each of its kinds |
| Karpenter's overview | `list` on node pools, node claims and nodes, and on pods in every namespace |
| The **Map** tab | `list` in the object's namespace on what it shows: pods, workloads, services, ingresses, network policies, autoscalers, disruption budgets, ConfigMaps, Secrets, service accounts and volume claims (and Gateway API gateways and routes, when the cluster serves them). Also `list` on nodes, persistent volumes and storage classes. A kind it can't list still appears where it's referenced, without a status, and so does a route's gateway or service in another namespace, which the map doesn't list. |
| Field explanations | The cluster's OpenAPI schema, which every account can read |

If a page needs something you can't read, it says **Access denied**, with *Your account isn't allowed to read this. If you only have access to some namespaces, pick one from the namespace menu.*

## Usage history

Charts over time come from a Prometheus-compatible server, reached through the API server's service proxy with your own credentials.

| To | Needs |
| --- | --- |
| Find the server automatically | `list` on `services`, in every namespace |
| Read history from it | `get` on `services/proxy` in the server's namespace |
| See [right-sizing](/metrics/right-sizing) recommendations | The two above, and `list` on Deployments, StatefulSets, DaemonSets, pods and HorizontalPodAutoscalers where you look. `list` on nodes, and on VerticalPodAutoscalers when the cluster serves them, helps but isn't needed: see [Without nodes or VerticalPodAutoscalers](/metrics/right-sizing#without-nodes-or-verticalpodautoscalers). |

Without `list` on services, choose the server yourself in **Metrics source**. See [Usage history](/metrics/usage-history).

## Helm releases

Lumovi reads releases from the Secrets (or ConfigMaps) Helm keeps them in, so looking at them needs `list` on `secrets` in their namespaces (or on `configmaps`, for releases kept there), and no `helm`. The built-in `view` ClusterRole doesn't include Secrets, so it isn't enough to see releases.

Changing a release runs your own `helm` with your credentials, so you need whatever Helm needs to change the release's objects. See [Helm releases](/helm/releases).

## Making changes

Each action checks one permission first:

| Action | Checks |
| --- | --- |
| Scale (Deployments, StatefulSets, ReplicaSets) | `patch` on the kind |
| Scale (custom kinds) | `patch` on the kind's `scale` subresource |
| Restart, change image, roll back, pause or resume a rollout | `patch` on the workload |
| Suspend or resume a CronJob or Job | `patch` on the kind |
| Run a CronJob now | `create` on `jobs` |
| Cordon, uncordon, drain | `patch` on `nodes` |
| Change an autoscaler's range, expand a volume | `patch` on the kind |
| Edit labels and annotations | `patch` on the kind |
| Edit YAML | `update` on the kind |
| Delete, restart a pod | `delete` on the kind |
| Evict a pod | `create` on `pods/eviction` |
| Open a shell | `create` on `pods/exec` |
| Open a shell on a node | `create` and `get` on `pods`, `create` on `pods/exec`, and `delete` on `pods`, in the node shells' namespace (`kube-system` unless set otherwise) |
| Add a debug container | `patch` on `pods/ephemeralcontainers` |
| Forward a port | `create` on `pods/portforward` |
| Apply a right-sizing recommendation | `patch` on the workload |
| A view's action that changes the object | `patch` on the kind, or on its `status` |
| A view's action that creates something, like **Back up now** | `create` on the kind it creates |

A few notes:

- **Draining** cordons the node, then evicts its pods a few at a time, so it also needs `create` on `pods/eviction`. A PodDisruptionBudget can refuse an eviction: the drain shows each pod's progress, with **Retry** for any that fail.
- **Debug containers** open a shell in the new container, which also needs `pods/exec`.
- **Shells on nodes** run in a privileged pod Lumovi creates, so that namespace's Pod Security must allow privileged pods. Without `delete`, the pod stays until its 12-hour deadline, and the tab says so before you start. See [Shells on nodes](/debug/node-shell).
- **[Terminals](/debug/terminal)** in the desktop app aren't checked: they're your own shell, and what you run there needs what it would in any terminal.
- **Create from YAML** and **several at once** don't check first. The cluster checks each object, and the dialog shows what it refused.

<Tip>
  To check a permission yourself, use `kubectl auth can-i`, for example `kubectl auth can-i create pods/exec -n shop`. Lumovi asks the cluster the same question.
</Tip>

## AI assistants

[AI assistants](/assistants/overview) use Lumovi with your credentials, like everything else in it: in the desktop app, your kubeconfig's; on a [server](/assistants/server), the ones you signed in with, so Lumovi impersonates you, or passes your own token on, as it does for your pages. An assistant can read and change only what your account can, and Lumovi gives it nothing of its own.

Lumovi doesn't ask the cluster up front for an assistant. It sends each change as a dry run first, which the API server checks against your RBAC like the real change, so one your account can't make fails there, before you're asked. Reading something you may not read fails the same way, and the assistant is told why. Once you approve a change, other than a deletion, it's tried as a dry run again, with the same permissions.

| Tool | Needs |
| --- | --- |
| `list_clusters` | Nothing: it reads your kubeconfig |
| `list_kinds` | API discovery, which every account can read |
| `list_resources` | `list` on the kind |
| `get_resource` | `get` on the kind |
| `get_events` | `list` on `events` |
| `get_logs` | `get` on `pods/log` |
| `find_problems` | `list` on nodes, pods, Deployments, StatefulSets, DaemonSets, Jobs, PersistentVolumeClaims and events, in the namespace or across the cluster. It names the kinds it couldn't list, and sums up the rest. |
| `apply_manifest` | `get` and `patch` on the kind, and `create` when it creates the object |
| `scale` | `get` and `patch` on the kind, or on its `scale` subresource for custom kinds |
| `restart` | `get` and `patch` on the workload |
| `delete_resource` | `get` and `delete` on the kind |
| `wait_for_change` | Nothing: it waits for your answer in Lumovi |

A cluster you made [read-only](/changes/read-only) refuses assistants' changes whatever your RBAC allows, and so does one whose **Changes they ask for** is **Never**. See [Approving changes](/assistants/approvals#changes-they-ask-for).

## An example

A teammate with the built-in `view` role can browse workloads and read logs. To let them see usage history from a Prometheus in `monitoring` too, bind a Role there:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lumovi-usage-history
  namespace: monitoring
rules:
  - apiGroups: [""]
    resources: ["services/proxy"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: lumovi-usage-history
  namespace: monitoring
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: lumovi-usage-history
subjects:
  - apiGroup: rbac.authorization.k8s.io
    kind: Group
    name: platform-team
```
