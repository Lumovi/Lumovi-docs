The desktop app shows every context in your kubeconfig, with the credentials it already has: client certificates, tokens, and credential plugins like `gke-gcloud-auth-plugin`, `aws eks get-token` and `kubelogin`. To add a cluster someone gave you a kubeconfig for, paste it in Lumovi: see [Add a cluster](#add-a-cluster).

<Note>
  **In your cluster:** Lumovi served from a cluster shows that one cluster, or a [fleet](/clusters/fleet) of clusters your team chose, and each person signs in with their own identity. There's no kubeconfig to read. A fleet opens on a page of its clusters, instead of the start screen. See [Run it in your cluster](/server/overview).
</Note>

## Where clusters come from

Lumovi finds your kubeconfig the same way `kubectl` does:

- The files listed in the `KUBECONFIG` environment variable, separated by `:` (`;` on Windows).
- Otherwise, `~/.kube/config`.

Or [choose the files](#choose-your-kubeconfig-files) in Lumovi, which keeps them. Clusters you [add in Lumovi](#add-a-cluster) come after the rest, each in a file of its own.

Several files are merged with kubectl's rules:

- Files that are missing or empty are skipped.
- When two files define a cluster, user or context with the same name, the first file wins.
- The current context is the first one any file sets.
- Relative paths in a file (to a certificate, say) are read from that file's folder.

Unlike kubectl, Lumovi still reads the other files when one can't be read: a notice above the list says so, like "~/.kube/staging.yaml couldn't be read, so its clusters aren't here.", with **Show in Finder**.

<Warning>
  A `KUBECONFIG` you export in your shell's startup file (`~/.zshrc`, `~/.bashrc`) reaches Lumovi only when you start it from that shell. Opened from the Dock, Spotlight or a launcher, it doesn't see the variable, and reads `~/.kube/config`. The kubeconfig files button, at the bottom of the start screen, shows which files were read. To always use your files, [choose them in Lumovi](#choose-your-kubeconfig-files), or see [Setting environment variables](/reference/environment-variables#setting-them).
</Warning>

When there's nothing to show, the start screen says why, with **Choose a kubeconfig…**:

- **Your kubeconfig couldn't be read**: the file, and the reason, in the parser's words. Fix it and choose **Reload**, or choose another file.
- **No clusters yet**: no file has a context. Choose the file you use with kubectl, or **Add a cluster**.
- **The kubeconfig you chose is gone**: a file you chose in Lumovi was moved or deleted. Choose another, or go **Back to KUBECONFIG and ~/.kube/config**.

The kubeconfig is read again each time you choose **Reload**, so you don't need to restart the app after changing it.

<Tip>
  Lumovi never writes your kubeconfig files. [Add a cluster](#add-a-cluster) in Lumovi, or add contexts with your cloud's CLI or `kubectl config`, then choose **Reload** on the start screen.
</Tip>

### Choose your kubeconfig files

The button at the bottom of the start screen names the first file Lumovi reads, and counts the others. It opens **Kubeconfig files**: every file Lumovi reads, merged as kubectl does, each with where it's from (**The default**, **From KUBECONFIG**, **Chosen in Lumovi**, **Added in Lumovi**, or **Clusters added in Lumovi** for Lumovi's own folder) and how many clusters it has, or why it has none.

- **Choose a kubeconfig…** reads only the files you pick, in place of `KUBECONFIG`'s or `~/.kube/config`.
- **Add another file…** reads one more, after the rest.
- **Back to KUBECONFIG and ~/.kube/config** undoes both.

Lumovi keeps your choice. Files you chose are read whatever `KUBECONFIG` says; files you added come after `KUBECONFIG`'s, whatever it is when Lumovi starts. [Terminals](/debug/terminal#kubectl-points-at-the-cluster) get the same files.

Each file has **Show in Finder** (**Show in Explorer** on Windows), and one you chose or added in Lumovi has **Remove**: "Lumovi reads these files and never writes to them. Removing one only stops Lumovi reading it." `KUBECONFIG`'s own files can't be removed here: change `KUBECONFIG`. A file you chose or added that's been moved or deleted says "Missing: it was moved or deleted", with **Choose it again…**.

Your organization's [policy](/desktop/policy#kubeconfigfiles) can keep Lumovi to `KUBECONFIG`'s files and `~/.kube/config`. The list then says "Your organization's policy keeps Lumovi to these files.", and nothing in it can be changed.

### Credential plugins

Contexts that get their credentials from a plugin (an `exec` entry in the kubeconfig) work as they do in a terminal. Lumovi keeps each context's configuration between requests, so a plugin's cached token is reused instead of asked for again.

On macOS and Linux, apps opened from the Dock or a launcher don't get the `PATH` your shell sets up. So when Lumovi starts, it asks your login shell for its `PATH`, and finds plugins wherever your shell would. It asks for your proxy too: see [Behind a proxy](#behind-a-proxy). If the shell takes longer than five seconds or fails, Lumovi keeps the `PATH` it started with. Windows apps already get the full `PATH`.

If a plugin isn't found, the cluster shows **Credentials failed**, with the message: *The credential plugin "gke-gcloud-auth-plugin" wasn't found. Install it, or make sure it's on your PATH.*

### Clusters on plain HTTP

A cluster served over `http://` (through `kubectl proxy`, for example) has to opt in to unencrypted connections, the same rule as the official JavaScript client. Set `insecure-skip-tls-verify: true` on the cluster in your kubeconfig:

```yaml ~/.kube/config
clusters:
  - name: local-proxy
    cluster:
      server: http://127.0.0.1:8001
      insecure-skip-tls-verify: true
```

Without it, the cluster shows **Plain HTTP blocked**.

### Behind a proxy

Lumovi reaches your clusters through the proxy your shell uses, from `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`, as `kubectl` does. A cluster with a `proxy-url` in your kubeconfig goes through that one instead:

```yaml ~/.kube/config
clusters:
  - name: production
    cluster:
      server: https://api.prod.example.com:6443
      proxy-url: http://proxy.corp.example.com:3128
```

See [Proxies and certificates on your computer](/desktop/network).

Each row shows:

- **A tile** in the cluster's color, with its letters, and its status on the tile's corner, pulsing while Lumovi asks the cluster for its version.
- **Its name**, with a **Production** badge if it's [production](#cluster-settings), a lock if it's [read-only](/changes/read-only), and **current** for your kubeconfig's current context.
- Under it, the API server's host and the user, like `api.example.com · admin`, or the context's name if you gave the cluster a [name of its own](#cluster-settings).
- **Its version and how long it took to answer** (`v1.34.1 · 18 ms`), or what went wrong.

The clusters you opened last, up to three, come first, under **Recent**. Then each is in the [group](#cluster-settings) you put it in, with **Other clusters** last. **Group by** groups them by a label's values instead, like `env=production`, or not at all, and Lumovi remembers which.

Type to search, by name, context, server or label: `env=production` finds the clusters with that label, and each row shows the label it matched. Move with <kbd>↑</kbd> <kbd>↓</kbd>, and press <kbd>↵</kbd> to open one.

A cluster you hide is left out, and the list's footer counts the hidden ones: choose **2 hidden** to show them, dimmed.

### A cluster's actions

Its **⋯**, a right-click, or <kbd>.</kbd> on the selected row opens its actions:

- **Open**.
- **Settings…** (<kbd>⌘</kbd><kbd>I</kbd>): see [Cluster settings](#cluster-settings).
- **Copy for kubectl**, for a cluster you added in Lumovi: see [Use it with kubectl](#use-it-with-kubectl).
- **Show in Finder**: the file it's read from.
- **Hide**, or **Show**.
- **Remove from Lumovi** (<kbd>⌘</kbd><kbd>⌫</kbd>), for a cluster you added in Lumovi: see [Change or remove it](#change-or-remove-it).

<kbd>⌘</kbd><kbd>N</kbd> [adds a cluster](#add-a-cluster). On Windows and Linux, use <kbd>Ctrl</kbd> instead of <kbd>⌘</kbd>.

### When a cluster can't be reached

The label says what kind of problem it is. Hover it for the full message. If you open the cluster anyway, the overview explains what to try, with **Try again** and **Choose another cluster**.

| Label | What it means | What to try |
| --- | --- | --- |
| **Unreachable** | Can't reach the cluster. | Check that the API server is running and reachable from this machine. A VPN or tunnel may be required. |
| **Timed out** | The cluster isn't responding. | The API server accepted the connection but didn't answer within 20 seconds. Set `LUMOVI_REQUEST_TIMEOUT_MS` for a slow one. |
| **Certificate error** | The cluster's certificate couldn't be verified. | Hover the label for which: not signed by the certificate authority in your kubeconfig, expired, or for another name. Behind a proxy that inspects HTTPS, see [Proxies and certificates](/desktop/network#when-it-doesn’t-connect). |
| **Plain HTTP blocked** | Plain HTTP isn't allowed. | Set `insecure-skip-tls-verify: true` on the cluster, as above. |
| **Credentials failed** | Couldn't get credentials. | The credential plugin for this context failed. Make sure it's installed and that you're logged in. |
| **Unauthorized** | Your credentials were rejected. | The token or certificate may have expired. Sign in again, then retry. |
| **Forbidden** | Access denied. | Your account isn't allowed to read this. If you only have access to some namespaces, pick one from the namespace menu. |
| **Not found** | Not found. | It may have been deleted, or this API isn't available on the cluster. |
| **Server error** | The API server returned an error. | This is usually temporary. Retry in a moment. |
| **Misconfigured** | The context can't be used as it is. Opened, its error screen says **Invalid request**. | Hover the label for the reason, like *Context "dev" points at cluster "dev-eu", which isn't defined*. Fix the context in your kubeconfig, then choose **Reload**. |

Expired credentials show up as **Unauthorized**, or as **Credentials failed** when the plugin that gets them fails. On the start screen, both read **Couldn't sign in**: hover it for which. Signing in again with your cloud's CLI usually fixes both.

## Add a cluster

To add a cluster you have a kubeconfig for, without changing your own files, choose **Add cluster** above the list (<kbd>⌘</kbd><kbd>N</kbd>). Paste the kubeconfig, or one context from it with its cluster and user. Or, under **A file**, drop the file or choose it: Lumovi copies what it needs, so the file can move or go. **Check it** then checks three things for each of its contexts, one after another, and says what it found:

1. **It reads as a kubeconfig**, with at least one context, and the cluster and user each context names.
2. **The server answers.** Lumovi asks it for its version, without any credentials, and shows the version and how long it took. A server that refuses whoever asks has answered too.
3. **The credentials work.** Lumovi signs in, and lists one namespace. Signed in but not allowed to list namespaces still counts.

Lumovi sends the credentials only to a server that answered: if its certificate doesn't hold, they're never sent, and to a server whose certificate isn't checked, only once you agree (see below). A check that fails says why, in the error's own words. **Add it anyway** keeps a cluster whose server didn't answer, like one behind a VPN that's off.

A cluster with a `proxy-url` says which proxy everything to it goes through, without the proxy's password.

### Credentials that run a program, send a file, or go unverified

Some credentials do more than sign in, so the check stops before them, and shows exactly what:

- **A [credential plugin](#credential-plugins)** (an `exec` user, or a `gcp` or `azure` auth provider's `cmd-path`) runs a program to sign in: "Signing in runs a program on this computer", with the command as it would run, and its environment.
- **A token file** (`token-file`, or an auth provider's `tokenFile`) sends a file on your computer to the server: Lumovi names the file, and each server it goes to.
- **A server that isn't verified** (`insecure-skip-tls-verify: true`) would get the credentials whoever answers at its address: Lumovi names the server. A server on [plain HTTP](#clusters-on-plain-http) is asked about the same way, with or without that flag, as anyone on the network in between could read what's sent to it, its credentials too. Lumovi itself connects to it only with the flag, but kubectl would either way, in a terminal or with the line for kubectl: without the flag, there's nothing Lumovi can check, so the button that allows it is **Add it anyway**, which keeps it for kubectl at once.

Nothing runs, no file is read, and no credentials go to such a server, until you choose **Allow and continue**: not to check the cluster, and not to keep it. Until then, the check asks the server only for its version, with no credentials. You agree to that command, that file going to that server, or that server, exactly: change any of it, even an argument, a variable or the server, and Lumovi asks again.

Once it's kept, it's used as any kubeconfig's is, each time Lumovi signs in to that cluster, the start screen's check included.

This protects you from a kubeconfig that does more than it says. It's Lumovi asking you, not a wall against the page itself: see [Your credentials](/reference/privacy-and-security#your-credentials).

### Where it's kept

Each cluster you add is a kubeconfig file of Lumovi's own, in the `clusters` folder of its [app data](/reference/privacy-and-security#what-it-keeps-on-your-computer), named after it, like `payments-us.yaml`. On macOS and Linux, only your account can read the folder and its files. Lumovi reads them after your own files, and never writes any file but these.

What it keeps is only what you added: each context, under its name, with its cluster and user, which Lumovi names `lumovi-` and 12 random characters, so that no other kubeconfig's cluster or user is ever taken for them. Comments, preferences and the current context are left out. It refuses:

- **A context name it already reads**, since kubectl would take the first one: "Already read: “prod”. kubectl would take that one, so name it otherwise." Give the new one another name.
- **A file named relative to the kubeconfig**, like `certificate-authority: ca.crt`: in Lumovi's folder, it wouldn't be found. Give its full path, or the certificate itself, in the `-data` field.
- **A file that isn't there, isn't a file, or is over 1 MB**, for a certificate, a key or a token: "It names /dev/zero, which isn't a file."

Done, it says "_payments-us_ is ready". Give it a name, a color and a group, as in its [settings](#cluster-settings), and copy the line that uses it with kubectl. **Open** opens it.

### Use it with kubectl

**Copy for kubectl**, in its actions and its settings, gives the line that has kubectl read the cluster, in any terminal:

```bash
export KUBECONFIG="$HOME/Library/Application Support/Lumovi/clusters/payments-us.yaml"
```

On Windows, it's PowerShell's: `$env:KUBECONFIG = "$HOME\AppData\Roaming\Lumovi\clusters\payments-us.yaml"`. Each path is quoted so that nothing in it is read as more than its text: one with a character a shell would read otherwise, like `$` or `!`, goes in single quotes instead. Lumovi's own [terminals](/debug/terminal) read it already.

### Change or remove it

A cluster you added has, in its settings, **Edit connection…**: the add dialog again with its kubeconfig, checked as it was when you added it. **Remove from Lumovi**, there or in its actions (<kbd>⌘</kbd><kbd>⌫</kbd>), deletes its file from Lumovi's folder, and with it any cluster added with it, from the same kubeconfig. Your own kubeconfig files aren't touched. A cluster from your own kubeconfig can't be changed or removed here: change your file.

Its kubeconfig comes back with each secret (a token, a password, a client key, an auth provider's tokens, the values of its program's environment, and a proxy's password) as `(kept by Lumovi)`, so they stay off your screen. Leave one as it is, and Lumovi keeps it, and checks the cluster with it; paste a new one in its place to change it. What it runs or sends, agreed to before, isn't asked again, unless you change it. A secret written into a program's arguments, like `--oidc-client-secret=…`, is shown as it's written.

If you change where it connects (its server, its proxy, how its certificate is checked, or, for a user that signs in with OIDC, its identity provider), or add a context that signs in as the same user, Lumovi asks before a kept secret, or a program you allowed, is used there.

Your organization's [policy](/desktop/policy#kubeconfigfiles) can keep Lumovi to the kubeconfig it manages: then you can't add clusters, and those you added aren't read until it's gone.

## Cluster settings

Each cluster has settings of Lumovi's own, kept in its settings and never in your kubeconfig: **Settings…** in its actions, or <kbd>⌘</kbd><kbd>I</kbd> on the start screen. They apply when you choose **Save**.

| Setting | What it does |
| --- | --- |
| **Name** | What Lumovi calls it: in the list, the cluster switcher, the command palette and the window's title. Its context's name, unless you set one. |
| **Color** | Its tile's color: one of eight, or none. |
| **Group** | The group it's in on the start screen. |
| **Labels** | Labels like `env=production`, to search and group by. |
| **Namespace** | The namespace it opens in. Setting it forgets the one you last picked there. |
| **Production** | Deleting and draining ask you to type its name, and its rows say **Production**. Until you set it, Lumovi guesses from the context's name: see [Production clusters get an extra check](/changes/safely#hard-to-do-by-accident). Once you set it, it stays as you set it, until **Let Lumovi guess from its name**. |
| **Read-only** | Lumovi changes nothing in it. See [Read-only mode](/changes/read-only). |
| **Hidden** | Left out of the list. Show hidden clusters from its footer. |

**Connection** says where the cluster comes from. One from your kubeconfig can't be changed here: "Lumovi never changes it: to change how it connects, edit the file.", with **Show in Finder**. One you [added in Lumovi](#add-a-cluster) shows its server and how it signs in, with **Edit connection…**, **Copy for kubectl** and **Remove from Lumovi**.

Settings are kept by the context's name: a context you rename in your kubeconfig starts without them.

## Switching clusters

The cluster switcher at the top of the sidebar shows the cluster you're in, by its [name in Lumovi](#cluster-settings), its Kubernetes version (or **Unavailable** when it doesn't answer), and a lock if it's [read-only](/changes/read-only). Open it to:

- Switch to another cluster: type to filter, and pick one.
- Go back to **All clusters**, the start screen.
- Turn **Read-only** on or off for this cluster.

You can also switch from the command palette (<kbd>⌘</kbd><kbd>K</kbd>), which lists every cluster and **All clusters**, or use **Go → All Clusters** (<kbd>⌘</kbd><kbd>⇧</kbd><kbd>C</kbd>) in the menu bar. On Windows and Linux, use <kbd>Ctrl</kbd> instead of <kbd>⌘</kbd>.

Each cluster remembers its own [namespace](/clusters/namespaces), so switching back puts you where you were.

<Note>
  **In your cluster:** a Lumovi that shows one cluster has nothing to switch to, so the switcher shows the cluster's name and address, and **Read-only**, which is the server's, for everyone: see [Read-only mode](/changes/read-only#in-your-cluster). In a [fleet](/clusters/fleet), the switcher and the command palette list every cluster you may see, and **All clusters** goes back to the fleet's page of clusters. A browser has no menu bar, so there's no <kbd>⌘</kbd><kbd>⇧</kbd><kbd>C</kbd>.
</Note>

## When a cluster stops answering

If a cluster stops responding while you're using it, a banner says *Can't reach production. Checking again every 15 seconds.*, with **Retry now**, and **All clusters** to open another. (When Lumovi runs [in your cluster](/server/overview) with one cluster, there's no other, so the banner has only **Retry now**. In a [fleet](/clusters/fleet), **All clusters** goes back to its page of clusters.) The last data stays on screen, so you can keep reading while it comes back. When a single list fails to refresh, it keeps its rows and says *Couldn't refresh — showing the last data.*, with **Retry**.

## Big or slow clusters

| Setting | Default | What it does |
| --- | --- | --- |
| `LUMOVI_MAX_LIST_ITEMS` | `5000` | The most objects a list loads. Lists are fetched in chunks of 500, and a longer list says so, with a way to filter by label. |
| `LUMOVI_REQUEST_TIMEOUT_MS` | `20000` | How long the API server has to answer. |

Both are read when the app starts. See [Environment variables](/reference/environment-variables).
